# 인프라 구성 명세 v2 (Book Eating Lion / Team3)

> 원본: [`terraform/인프라구성명세.md`](./인프라구성명세.md)  
> 검증 기준: `dev` 브랜치 `7f8da9a` 이후 로컬 작업, 2026-08-27  
> 목적: 원본을 보존하면서 실제 AWS 운영 상태, integrated/split 이중 운영 모델,
> SSM 기반 CD와 S3 Vectors 초기 적재 절차를 반영한 후속 명세

## 1. 결론

현재 **integrated 운영 모델은 dev/prod 모두 실제 배포 및 CD 검증이 완료**됐다.
`dev.ajttk.com`과 `book.ajttk.com`은 하나의 EKS 클러스터
`lion-team3-integrated` 안의 `dev`/`prod` namespace로 분리 운영된다.

반면 **split 운영 모델은 Terraform 코드 구조는 완성됐지만 실제 동시 배포 검증은
완료되지 않았다.** split dev runtime은 현재 운영하지 않고, split prod의 전용 VPC,
Aurora PostgreSQL, RDS Proxy, EKS 및 GitHub Actions IAM Role도 아직 실제 생성되지 않았다.

따라서 프로젝트 요구사항 충족 상태는 다음과 같이 판단한다.

| 요구사항 | 코드 | 실제 운영 검증 | 판정 |
| --- | --- | --- | --- |
| 하나의 EKS에서 dev/prod namespace 분리 | 완료 | 완료 | 충족 |
| dev/prod 독립 VPC·데이터·EKS 동시 구성 | 완료 | 미완료 | 부분 충족 |
| CloudFront + WAF + HTTPS + Route53 | 완료 | dev/prod 완료 | 충족 |
| EKS RollingUpdate 무중단 배포 | 완료 | dev/prod CD 성공 | 충족 |
| HPA + Karpenter 확장 | 완료 | 리소스 배포 확인, 부하 검증 별도 | 부분 충족 |
| prod Aurora Multi-AZ + RDS Proxy | split prod 코드 완료 | integrated 운영에는 미적용 | 부분 충족 |
| SQS + DLQ 기반 EPUB 비동기 색인 | 완료 | 큐/IAM/CD 완료, 초기 벡터 미적재 | 부분 충족 |
| S3 Vectors 기반 추천/RAG | 완료 | 인덱스 생성, 데이터 0건 | 부분 충족 |
| GitHub Actions OIDC + 환경 격리 | 완료 | dev/prod CD 성공 | 충족 |
| Terraform/SSM 단일 원본 설정 관리 | 완료 | plan 수렴 및 CD 성공 | 충족 |

## 3. 지원하는 운영 모델

### 3.1 Integrated

현재 운영 중인 구성이다.

| 구분 | dev | prod |
| --- | --- | --- |
| EKS | `lion-team3-integrated` 공유 | `lion-team3-integrated` 공유 |
| Namespace | `dev` | `prod` |
| 도메인 | `dev.ajttk.com` | `book.ajttk.com` |
| PostgreSQL | dev EC2 인스턴스의 `bookdb_dev` | 같은 EC2 인스턴스의 `bookdb_prod` |
| DB 스키마 | `catalog_db`, `order_db`, `member_db`, `ai_db` | 동일 |
| Valkey | dev 전용 | integrated prod 전용 |
| Cognito | dev 전용 | integrated prod 전용 |
| SQS/DLQ | dev 전용 | integrated prod 전용 |
| 프런트엔드/미디어 S3 | dev 전용 | prod 전용 |
| S3 Vectors | `lion-team3-dev-vectors` | `lion-team3-prod-vectors` |
| GitHub Environment | `integrated-dev` | `integrated-prod` |

Integrated는 비용 절감을 위한 현재 운영 형태다. DB는 물리 EC2 인스턴스를 공유하지만
논리 데이터베이스와 애플리케이션 namespace, 캐시, 인증, 큐, 객체 저장소 및 벡터
저장소는 환경별로 분리한다.

### 3.2 Split

환경별로 다음 계층을 독립 생성한다.

```text
terraform/environments/dev/{00-base,01-data,02-runtime}
terraform/environments/prod/{00-base,01-data,02-runtime,03-deploy}
```

- dev: VPC `10.13.0.0/16`, EC2 PostgreSQL, dev EKS
- prod: VPC `10.14.0.0/16`, Aurora PostgreSQL Multi-AZ, RDS Proxy, prod EKS
- Terraform state와 GitHub Environment도 환경별로 분리

현재 split prod는 설계와 코드만 존재한다. 실제 완성 판정에는 다음 검증이 필요하다.

1. prod `00-base → 01-data → 02-runtime` 최초 apply
2. `github-actions-lion-team3-prod` 생성 후 GitHub `prod` Environment 연결
3. prod EKS CD 및 도메인 전환 검증
4. Aurora/RDS Proxy 연결, Multi-AZ 장애 복구 및 부하 테스트
5. integrated와 split 간 컷백 런북 검증

## 4. Cutover 안전 규칙

`enable_dev_cutover`는 `dev.ajttk.com`의 CloudFront/Route53 소유권을 integrated
runtime이 가질지 결정한다.

- `true`: integrated가 dev 도메인을 제공한다. **현재 운영값**이다.
- `false`: integrated의 dev edge 리소스를 제거한다. split dev가 도메인을 다시
  제공할 준비가 끝난 의도적 컷백에서만 사용한다.

운영 상태와 코드 기본값을 일치시키기 위해
`terraform/environments/integrated/02-runtime/terraform.tfvars`는 `true`를 저장한다.
컷백은 별도 PR에서 다음 순서를 지킨다.

1. split dev runtime과 프런트엔드가 정상인지 임시 엔드포인트로 확인
2. DNS/CloudFront 전환 계획과 롤백 기준 확인
3. `enable_dev_cutover=false` 변경 PR 검토
4. destroy가 아닌 saved plan으로 dev edge 변경만 확인
5. apply 후 `dev.ajttk.com` 홈페이지/API/표지 확인

## 5. Terraform 계층과 SSM

각 운영 모델은 다음 순서를 지킨다.

```text
00-base → 01-data → 02-runtime → 애플리케이션 CD
```

AWS가 생성·결정하는 동적 값은 SSM Parameter Store가 단일 원본이다.

- 네트워크: `/{infra}/network/*`
- 스토리지: `/{data}/storage/*`
- DB/캐시: `/{data}/data/*`
- Cognito: `/{data}/auth/*`
- SQS: `/{data}/ai/*`
- Edge: `/{infra}/edge/*`, integrated dev는 `/integrated/dev/edge/*`
- IRSA: `/{infra}/ai/*`, `/{infra}/member/*`

GitHub Environment Variables에는 다음 세 개만 둔다.

- `AWS_REGION`
- `AWS_ROLE_ARN`
- `K8S_NAMESPACE`

워크플로는 OIDC 인증 후 `scripts/load-deployment-config.sh`로 SSM 값을 읽는다.
GitHub Actions IAM은 자기 환경 prefix만 읽을 수 있으며 integrated 역할만 integrated
dev 배포를 위해 `/dev/*`를 추가로 읽는다.

## 6. CI/CD와 다운타임

백엔드 배포는 Kubernetes RollingUpdate를 사용한다.

- `maxUnavailable: 0`
- readiness/startup probe 통과 후 기존 Pod 제거
- 서비스별 독립 빌드·ECR push·rollout 확인
- 실패 시 rollback 단계 수행

2026-08-27에 integrated dev/prod 백엔드 4종과 프런트엔드 CD를 각각 검증했다.
홈페이지와 `/api/catalog/books`는 양쪽 모두 HTTP 200이었다.

프런트엔드는 S3 `sync --delete` 후 CloudFront invalidation을 수행한다. 사이트 전체를
중단하지는 않지만, 캐시된 구 HTML이 이미 삭제된 해시 자산을 참조하는 짧은 404
가능성은 남는다. 완전한 원자적 배포가 필요하면 버전 prefix+원점 전환 방식이 후속
개선안이다.

## 7. S3 Vectors와 초기 적재

환경마다 다음 리소스를 독립 사용한다.

- 벡터 버킷: `lion-team3-{env}-vectors`
- 추천 인덱스: `recommendation-books-v1`
- 구매도서 RAG 인덱스: `wiki-v1`
- 타입/차원/거리: `float32`, `1024`, `cosine`
- `wiki-v1`: `text`를 non-filterable metadata로 설정

2026-08-27 확인 시 dev/prod의 두 인덱스 모두 0건이었다. 인덱스 생성은 완료됐지만
기능 데이터 초기화는 별도 수행해야 한다.

### 7.1 추천 인덱스 backfill

관리자 JWT로 다음 API를 호출한다.

```http
POST /api/catalog/admin/books/recommendation-index/rebuild
Authorization: Bearer <ADMIN_JWT>
```

판매 중인 활성 도서를 Redis Streams에 발행하고 AI 서비스가 Bedrock 임베딩 후
`recommendation-books-v1`에 upsert한다.

### 7.2 EPUB/RAG 인덱스 backfill

새로 추가한 복구 API를 사용한다.

```http
POST /api/catalog/admin/books/ingest-index/rebuild
Authorization: Bearer <ADMIN_JWT>
```

삭제되지 않고 EPUB S3 Key가 있는 모든 도서를 기존 SQS ingest 파이프라인에 다시
발행한다. AI 서비스는 S3 EPUB 다운로드, 텍스트 분할, Bedrock 임베딩, 벡터 건수
검증 후에만 `wiki_books`를 등록한다.

동일 `source_hash`는 임베딩을 생략하고, 벡터 키가 결정적이므로 반복 실행이
가능하다. 다만 Bedrock 비용과 처리 시간을 고려해 dev에서 먼저 검증한 후 prod를
순차 실행한다.

### 7.3 완료 확인

```bash
aws s3vectors list-vectors \
  --vector-bucket-name lion-team3-{env}-vectors \
  --index-name recommendation-books-v1 \
  --region ap-northeast-2

aws s3vectors list-vectors \
  --vector-bucket-name lion-team3-{env}-vectors \
  --index-name wiki-v1 \
  --region ap-northeast-2
```

추가로 ingest/purchase DLQ, AI Pod 로그와 `ai_db.wiki_books` 등록 결과를 확인한다.

## 8. 보안 및 격리

- 모든 AWS 리소스에 `Team=Team3` 기본 태그 적용
- DB/Valkey는 private subnet 및 app security group으로 제한
- DB 비밀번호는 Secrets Manager에서 관리
- GitHub Actions는 장기 Access Key 대신 OIDC 사용
- AI/member Pod는 IRSA를 사용
- S3 frontend/media는 public access block과 CloudFront OAC 사용
- SQS는 SSE와 DLQ 사용
- EKS는 서비스별 NetworkPolicy와 namespace 격리 사용
- dev/prod DB 계정 권한은 현재 상태를 유지하고 스키마 구조를 동일하게 관리
