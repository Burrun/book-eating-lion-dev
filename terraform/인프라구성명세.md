## 1. 팀 공유 계정 규칙 (가장 중요)

이 프로젝트는 **여러 팀이 같은 AWS 계정을 공유**합니다 (`061039804626`). 리소스에 팀 태그가 없으면 같은 팀원조차 그 리소스를 관리할 수 없고, 다른 팀이 실수로 우리 리소스를 건드릴 위험도 있습니다.

- **모든 리소스에 `Team = Team3` 태그가 반드시 붙어야 합니다.**
- 이 프로젝트는 `provider.tf`의 `default_tags`로 이걸 자동화했습니다(§5 참고) — 개별 리소스에 태그를 직접 안 붙여도 됩니다. **단, Karpenter가 EC2 API를 직접 호출해 만드는 노드는 예외**이므로 `modules/compute/karpenter/main.tf`의 `EC2NodeClass` `tags` 블록에 별도로 명시돼 있습니다.
- 콘솔에서 수동으로 뭔가 만들 일이 생기면(디버깅용 임시 리소스 등) 반드시 `Team=Team3` 태그를 직접 추가하세요.

## 2. 인프라 구성 개요 — dev / prod

이 프로젝트는 **dev와 prod가 완전히 분리된 VPC와 Terraform State**를 씁니다. 모듈(코드)은 동일하고, 환경별 `terraform.tfvars` 값만 다르게 넣어서 두 개의 독립된 인프라를 만듭니다. 같은 AWS 계정 안에 둘 다 떠 있어도 CIDR이 겹치지 않게 분리돼 있습니다.

### 2.1 계층별로 실제 만들어지는 리소스 (dev/prod 공통 구조)

| 계층 | 만들어지는 리소스 |
| --- | --- |
| **00-base** | VPC(Public/App/Data 서브넷 각 2개, 2AZ), Internet Gateway, NAT Gateway 2개, Route Table 3종, Route53 Hosted Zone, ACM 인증서(`us-east-1`), WAF WebACL(CloudFront용, `us-east-1`), S3 버킷 2개(프론트엔드 정적 호스팅 / 미디어), ECR 레포 4개(`catalog`/`order`/`member`/`ai`), SNS 알림 Topic, GitHub OIDC Provider + IAM Role |
| **01-data** | (DB — 아래 2.2 참고), ElastiCache Valkey 8.2, Cognito User Pool + App Client + Domain, SQS 신간 등록 이벤트 큐 + DLQ |
| **02-runtime** | EKS 클러스터 v1.30 + 시스템 노드그룹, Karpenter(노드 오토스케일러 컨트롤러 + IAM/SQS/EventBridge), AWS Load Balancer Controller + ingress-nginx(NLB 프로비저닝), CloudFront 배포(S3+ALB 오리진, WAF 연결) + Route53 ALIAS 레코드, AI 서비스 IAM Role(IRSA — Bedrock 호출 + 이벤트 소비) |

### 2.2 dev와 prod가 다른 부분

| 항목 | dev | prod |
| --- | --- | --- |
| VPC CIDR | `10.14.0.0/16` (이정제님 할당 대역, dev/prod 동시 운영 안 해서 공유 — 2026-08-20) | `10.14.0.0/16` |
| 도메인 | `dev.ajttk.com` (별도 Route53 Zone) | `book.ajttk.com` |
| **DB** | **Aurora 대신 EC2 1대 + PostgreSQL 직접 설치** (`modules/dev_tools/ec2_postgres`) | **Aurora PostgreSQL 클러스터**(Writer + Reader) **+ RDS Proxy** |
| DB 삭제 보호 | 없음 (테스트 편의) | `deletion_protection=true`, 삭제 시 최종 스냅샷 남김 |
| Valkey 구성 | 단일 노드 (`replica_count=0`) | Primary + Replica (`replica_count=1`) |
| GitHub OIDC Provider | dev/prod 둘 다 생성 안 함 — 이 공유 계정에 이미 있는(우리 프로젝트와 무관한) Provider를 데이터소스로 조회만 (2026-08-20 확인) | 위와 동일 |
| tfstate | `book-eating-lion-tfstate-dev` | `book-eating-lion-tfstate-prod` (완전 별도 상태) |

**DB를 다르게 쓰는 이유:** dev는 상시 켜두는 환경인데 Aurora(Multi-AZ, Serverless v2도 최소 0.5 ACU부터 시간당 과금)를 계속 띄워두기엔 비용이 안 맞습니다. 그래서 dev만 EC2 한 대에 PostgreSQL을 직접 깔아 비용을 줄이고, 나머지 EKS/네트워크 구조는 prod와 동일하게 유지해 실서비스 조건을 최대한 재현합니다. 두 모듈의 출력값 이름을 동일하게 맞춰서 `02-runtime`은 dev/prod 분기 없이 같은 SSM 키로 DB endpoint를 읽습니다.

**도메인(`ajttk.com`) 관련 참고 (2026-08-20 확정):** 이 도메인은 이정제님이 Route53 Domains로 이미 등록해둔 실제 도메인입니다. apex(`ajttk.com`)와 `api`/`grafana` 서브도메인은 예전 프로젝트가 쓰던 레코드라 이 프로젝트는 건드리지 않고, dev/prod 각각 `dev.ajttk.com`/`book.ajttk.com` 서브도메인만 새로 씁니다. 부모 Zone에 대한 NS 위임 레코드는 콘솔에서 수동으로 추가하지 않고 `modules/base/dns_zone`의 `aws_route53_record.delegation` 리소스가 `terraform apply` 한 번으로 자동으로 만듭니다(`var.parent_zone_domain = "ajttk.com"`, dev/prod 둘 다 이 모듈을 재사용).

## 3. 공통 원칙

- AWS 리전은 항상 **`ap-northeast-2`**(서울)만 씁니다. 예외: CloudFront용 ACM 인증서/WAF WebACL은 AWS 제약상 `us-east-1`에서만 발급 가능해서 그 두 리소스만 provider alias로 `us-east-1`을 씁니다(§6 참고).
- Access Key, DB 비밀번호, 인증서, 토큰은 GitHub/Notion/발표자료/화면 캡처에 노출하지 않습니다. 이 프로젝트는 DB 마스터 비밀번호를 `manage_master_user_password = true`(Aurora) 또는 Secrets Manager(`ec2_postgres`)로 관리해 tfvars/state에 평문이 남지 않게 합니다.
- 데이터베이스(Aurora, dev의 EC2 PostgreSQL)는 Private Subnet에만 두고 외부에 직접 공개하지 않습니다. 접근은 App Subnet의 보안그룹(`app_security_group_id`)에서만 허용합니다.
- 비용이 크게 발생할 수 있는 리소스(NAT Gateway, Aurora Multi-AZ reader, EKS 노드, ALB/NLB, CloudFront)는 새로 만들거나 스펙을 올리기 전에 팀원과 확인합니다.
- Terraform state는 계층별로 완전히 분리돼 있습니다(00-base / 01-data / 02-runtime) — 한 계층을 apply해도 다른 계층 state에는 손대지 않습니다.

## 5. 태그 규칙

`provider "aws"`의 `default_tags`로 전체 리소스에 자동 적용됩니다. 6개 파일(`environments/{dev,prod}/{00-base,01-data,02-runtime}/provider.tf`)에 동일하게 설정돼 있습니다.

| Key | Value | 비고 |
| --- | --- | --- |
| Project | `lion` | 코스/계정 차원 프로젝트 식별자 (리소스 네이밍 접두사 `lion-team3`와는 별개) |
| Team | `Team3` | §1의 계정 공유 규칙 핵심 태그 |
| Owner | `likelion-cloud6-team3` | 팀원 개인 실명 대신 프로젝트/팀 식별자 사용 |
| Environment | `dev` 또는 `prod` | `var.environment` 값 그대로 |
| ManagedBy | `terraform` (Karpenter 노드는 `karpenter`) | |
| Layer | `base` / `data` / `runtime` | 어느 state 계층이 만들었는지 |

> Karpenter가 EC2 API로 직접 만드는 노드(`EC2NodeClass`)는 `default_tags`를 상속받지 못해서 `modules/compute/karpenter/main.tf`에 위 표와 동일한 Project/Team/Owner를 별도로 명시했습니다.

## 6. 리전 예외 — `us-east-1` provider alias

CloudFront는 `us-east-1`에서 발급된 ACM 인증서와 `CLOUDFRONT` 스코프 WAF만 받을 수 있습니다(AWS 고정 제약). 그래서 `00-base`의 `acm_cert`, `waf` 두 모듈만 `providers = { aws = aws.us_east_1 }`로 호출합니다. 나머지 모든 리소스는 `ap-northeast-2`입니다.

## 7. 배포 절차 (Terraform 배포 런북)

### 7.1 사전 준비

- [ ] `aws sts get-caller-identity`로 자격 증명 확인 (리전: `ap-northeast-2`)
- [ ] Terraform `>= 1.8.0` 설치 확인
- [ ] **State 백엔드가 미리 존재해야 함** — `book-eating-lion-tfstate-{env}` S3 버킷과 `book-eating-lion-tflock-{env}` DynamoDB 테이블(dev/prod 각각). 이 저장소엔 이 둘을 만드는 부트스트랩 코드가 없으므로 **최초 1회는 수동으로(또는 별도 부트스트랩 스크립트로) 먼저 만들어야** `terraform init`이 됩니다.
- [ ] `terraform.tfvars`의 TODO 표시된 placeholder 값(도메인, S3 버킷명, 알림 이메일 등) 실제 값으로 교체 확인

### 7.2 환경 간 순서 — 없음 (dev/prod 독립적으로 apply 가능)

GitHub OIDC Provider(`aws_iam_openid_connect_provider`)는 AWS 계정당 URL 하나에 유일한 전역 리소스라, 원래는 "prod가 생성하고 dev는 조회만" 하는 모델을 쓰려 했습니다. 그런데 이 계정은 여러 팀이 공유하고 있고, 이미 (우리 프로젝트와 무관한) GitHub OIDC Provider가 그 URL에 존재합니다(2026-08-20 확인, 2025-12-23 생성). 그래서 **dev/prod 둘 다 `create_oidc_provider = false`**로 두고 기존 Provider를 데이터소스로 조회만 합니다. 결과적으로 dev/prod 사이에 apply 순서 의존성이 없습니다 — 각 환경은 §7.3의 계층 순서(00-base → 01-data → 02-runtime)만 지키면 됩니다.

### 7.3 계층 순서 (환경 하나 기준: `dev` 또는 `prod`)

```
00-base → 01-data → 02-runtime
```

각 계층은 상위 계층의 출력을 SSM Parameter Store로 조회하므로 반드시 이 순서로 apply해야 합니다(`docs/개발 문서/TERRAFORM_STRUCTURE.md` §4). `{env}`를 `dev` 또는 `prod`로 바꿔서 그대로 실행합니다.

```bash
# 1. Base 계층 (VPC, 서브넷, ECR, S3, Route53, ACM, WAF, SNS, GitHub OIDC)
cd terraform/environments/{env}/00-base
terraform init
terraform plan -out=tfplan
terraform apply tfplan

# 2. Data 계층 (dev: EC2 PostgreSQL / prod: Aurora, RDS Proxy, Valkey, Cognito)
cd ../01-data
terraform init
terraform plan -out=tfplan
terraform apply tfplan

# 3. Runtime 계층 (EKS → Karpenter → ALB Controller → CloudFront/AI IRSA)
cd ../02-runtime
terraform init
# 3-1. 클러스터부터 먼저 생성 — Karpenter/ALB Controller의 kubernetes/helm provider가
#      인증할 EKS 클러스터가 아직 없으면 이 단계에서 provider 초기화 자체가 실패한다.
terraform apply -target=module.eks_cluster
# 3-2. 나머지(Karpenter, ALB Controller, edge_routing, AI 서비스 IAM) 적용
terraform plan -out=tfplan
terraform apply tfplan
```

> **왜 `plan -out` 후 사람이 확인하고 `apply tfplan`을 쓰는가:** `00-base`/`01-data`는 위험 등급 **Critical**입니다(계층별 위험도 매트릭스는 `docs/개발 문서/TERRAFORM_STRUCTURE.md` §1 참고). `-auto-approve`는 쓰지 않고, diff를 사람이 읽은 뒤 승인하는 2단계를 항상 거칩니다. `02-runtime`도 신규 인프라를 처음 세울 때는 동일 절차를 따르되, 이후 반복 배포(서비스 라우트 추가 등)부터는 팀 판단에 따라 CI로 자동화해도 됩니다.

### 7.4 자원 정리 및 삭제 순서 (배포 역순)

```bash
cd terraform/environments/{env}/02-runtime && terraform plan -destroy -out=destroy.tfplan && terraform apply destroy.tfplan
cd ../01-data                                && terraform plan -destroy -out=destroy.tfplan && terraform apply destroy.tfplan
cd ../00-base                                && terraform plan -destroy -out=destroy.tfplan && terraform apply destroy.tfplan
```

> `01-data`는 Aurora/Valkey 등 영속 데이터를 담은 Critical 계층이라 삭제 전 반드시 `plan -destroy`로 무엇이 지워지는지 사람이 먼저 확인합니다. dev처럼 데이터 유실이 문제되지 않는 환경에서만 팀 판단으로 `-auto-approve`를 써도 됩니다. dev/prod는 서로 독립적이라(§7.2) 어느 쪽부터 삭제해도 상관없습니다.

## 8. 보안 원칙

- **보안그룹은 최소 권한**: DB(Aurora/EC2 PostgreSQL)·Valkey·RDS Proxy 보안그룹은 전부 `app_security_group_id`(EKS 노드/Pod 공용 SG)에서만 인바운드를 엽니다. `0.0.0.0/0`은 CloudFront/ALB의 80/443 등 정말 외부 공개가 필요한 곳에만 씁니다.
- **DB 비밀번호는 평문으로 두지 않음**: Aurora는 `manage_master_user_password = true`(AWS가 Secrets Manager에 자동 발급), dev의 EC2 PostgreSQL은 `random_password` + Secrets Manager를 쓰고 인스턴스가 부팅 시점에 직접 읽어옵니다. `user_data`/tfvars/state에 비밀번호 문자열을 절대 넣지 않습니다.
- **DB는 Private Subnet에만**: Aurora와 dev EC2 PostgreSQL 모두 Data 또는 App Subnet(Private)에 위치하고 Public IP가 없습니다. dev EC2 PostgreSQL은 SSH도 안 열고 SSM Session Manager로만 접속합니다.
- **CI/CD 권한은 최소 스코프**: GitHub Actions는 OIDC로 인증하고, 트러스트 정책의 `sub` 조건을 이 저장소(`Burrun/book-eating-lion-dev`, dev/prod가 공유하는 유일한 repo)로 제한합니다. EKS 배포 권한은 `aws_eks_access_entry`로 이 Role에만 명시적으로 부여합니다 — 단, `main-cd.yml`이 `k8s/base/03-secret.yaml`도 같이 적용하기 때문에 access policy는 `AmazonEKSAdminPolicy`를 씁니다(더 좁은 `AmazonEKSEditPolicy`는 secrets 리소스 권한이 빠져 있어 Secret apply가 깨짐 — 2026-08-20 확인). 진짜 최소권한화하려면 AWS 관리형 정책 대신 이 Role 전용 K8s ClusterRole을 따로 만들어야 하는데 아직 미구현.
- **CloudFront 뒤가 아니면 S3에 직접 접근 불가**: 프론트엔드/미디어 버킷은 CloudFront Origin Access Control(OAC)로만 접근을 허용하고 버킷을 퍼블릭으로 열지 않습니다.
- **저장 데이터 암호화**: Aurora는 `storage_encrypted = true`, S3 버킷 2개는 SSE(AES256)를 명시적으로 켭니다(둘 다 기본값이 꺼짐이라 빼먹기 쉬움).
- **EKS API 서버 접근 제한 가능**: `endpoint_public_access`는 켜져 있지만(GitHub-hosted runner의 IP 대역이 넓어 기본은 전체 허용) `public_access_cidrs` 변수로 좁힐 수 있습니다. self-hosted runner나 VPN을 쓰게 되면 이 값을 실제로 제한할 것.
- **dev EC2 PostgreSQL은 IMDSv2 강제**: `metadata_options.http_tokens = "required"`로 IMDSv1을 막습니다.

## 9. 프로젝트 종료 후 리소스 정리

기본 절차는 §7.4의 배포 역순 `terraform destroy`(`02-runtime` → `01-data` → `00-base`)입니다. 그것만으로 안 지워지거나 별도 확인이 필요한 항목들:

- [ ] S3 버킷(frontend/media) 내부 오브젝트를 먼저 비운다 — 안이 안 비어 있으면 `terraform destroy`가 실패함(버저닝이 켜져 있으면 버전까지 전부 삭제해야 함)
- [ ] ECR 레포에 남은 이미지 확인 — `image_tag_mutability=IMMUTABLE` + lifecycle policy(최근 30개 유지)라 오래된 태그는 자동 정리되지만, repo 자체를 지우려면 이미지가 안 남아있어야 함(필요시 force delete)
- [ ] Aurora 최종 스냅샷 확인 — prod는 `skip_final_snapshot=false`라 클러스터 삭제 시 스냅샷이 자동으로 남는다. 스냅샷도 비용이 발생하니 필요 없으면 별도로 지운다
- [ ] Secrets Manager 시크릿(Aurora master, EC2 PostgreSQL) — 삭제해도 기본 7~30일 복구 대기 기간 동안 과금되니, 필요 없으면 즉시 삭제(force delete) 검토
- [ ] CloudWatch Log Group 확인 — EKS control plane, Karpenter, `amazon-cloudwatch-observability` 애드온이 만드는 로그 그룹은 Terraform이 직접 관리하지 않아 클러스터를 지워도 자동으로 안 지워질 수 있음
- [ ] NAT Gateway / Elastic IP 재확인 — `00-base` destroy에 포함되지만, destroy가 중간에 실패해 멈추면 그대로 과금되는 대표 리소스라 꼭 다시 확인
- [ ] GitHub OIDC Provider는 dev/prod 둘 다 소유하지 않는 공유 계정 리소스라(§7.2) 우리가 지울 대상이 아님 — 삭제 순서 신경 안 써도 됨
- [ ] Route53 Hosted Zone — 도메인을 계속 쓸 계획이면 Zone은 남기고 그 안의 레코드만 정리한다(Zone 자체를 지우면 네임서버가 바뀌어 재등록이 필요함)
- [ ] `terraform state list`로 각 계층(00-base/01-data/02-runtime)에 남은 리소스가 없는지 최종 확인
- [ ] 남아 있는 비용 발생 리소스 최종 확인 후 팀에 공유
