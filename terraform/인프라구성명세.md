> 이 문서는 부트캠프 공용 템플릿("인프라구성명세.md")을 이 프로젝트에 실제로 맞게 처음부터 다시 쓴 문서입니다. 원본 템플릿은 EC2 1대 + RDS 1대를 콘솔에서 수동으로 만드는 최소 구성을 가정했지만, 이 프로젝트("책 먹는 사자")는 **Terraform으로 관리하는 계층형 VPC + EKS + Aurora + Karpenter** 구조라 원본의 EC2/RDS 콘솔 가이드, 수동 태그 절차, 확장 구성 로드맵 대부분이 그대로 적용되지 않습니다. 그래서 여기서는 **이 프로젝트에서 실제로 지켜야 하는 규칙만** 담습니다.

## 1. 팀 공유 계정 규칙 (가장 중요)

이 프로젝트는 **여러 팀이 같은 AWS 계정을 공유**합니다 (`061039804626`). 리소스에 팀 태그가 없으면 같은 팀원조차 그 리소스를 관리할 수 없고, 다른 팀이 실수로 우리 리소스를 건드릴 위험도 있습니다.

- **모든 리소스에 `Team = Team3` 태그가 반드시 붙어야 합니다.**
- 이 프로젝트는 `provider.tf`의 `default_tags`로 이걸 자동화했습니다(§5 참고) — 개별 리소스에 태그를 직접 안 붙여도 됩니다. **단, Karpenter가 EC2 API를 직접 호출해 만드는 노드는 예외**이므로 `modules/compute/karpenter/main.tf`의 `EC2NodeClass` `tags` 블록에 별도로 명시돼 있습니다.
- 콘솔에서 수동으로 뭔가 만들 일이 생기면(디버깅용 임시 리소스 등) 반드시 `Team=Team3` 태그를 직접 추가하세요.

## 2. 인프라 구성 개요 — dev / prod

이 프로젝트는 **dev와 prod가 완전히 분리된 VPC와 Terraform State**를 씁니다. 모듈(코드)은 동일하고, 환경별 `terraform.tfvars` 값만 다르게 넣어서 두 개의 독립된 인프라를 만듭니다. 같은 AWS 계정 안에 둘 다 떠 있어도 CIDR이 겹치지 않게 분리돼 있습니다.

### 2.1 계층별로 실제 만들어지는 리소스 (dev/prod 공통 구조)

| 계층 | 만들어지는 리소스 |
| --- | --- |
| **00-base** | VPC(Public/App/Data 서브넷 각 2개, 2AZ), Internet Gateway, NAT Gateway 2개, Route Table 3종, Route53 Hosted Zone, ACM 인증서(`us-east-1`), WAF WebACL(CloudFront용, `us-east-1`), S3 버킷 2개(프론트엔드 정적 호스팅 / 미디어), ECR 레포 4개(`catalog`/`order`/`member`/`ai`), SNS 알림 Topic, GitHub OIDC Provider + IAM Role |
| **01-data** | (DB — 아래 2.2 참고), ElastiCache Valkey 8.2, Cognito User Pool + App Client + Domain, SQS 신간 등록/구매 확정 이벤트 큐 + DLQ 각각 |
| **02-runtime** | EKS 클러스터 v1.34(EKS 지원 정책상 주기적으로 최신화 필요 — v1.30은 2026-08-20 기준 지원 종료로 교체됨) + 시스템 노드그룹, Karpenter(노드 오토스케일러 컨트롤러 + IAM/SQS/EventBridge), AWS Load Balancer Controller + ingress-nginx(NLB 프로비저닝), CloudFront 배포(S3+ALB 오리진, WAF 연결) + Route53 ALIAS 레코드, AI 서비스 IAM Role(IRSA — Bedrock 호출 + 이벤트 소비) |

### 2.2 dev와 prod가 다른 부분

| 항목 | dev | prod |
| --- | --- | --- |
| VPC CIDR | `10.13.0.0/16` (별도 승인받은 대역, prod와 분리) | `10.14.0.0/16` (계정 소유자 할당 대역) — 두 값 모두 `modules/base/network_plan`에서 단일 관리 |
| 도메인 | `dev.ajttk.com` (별도 Route53 Zone) | `book.ajttk.com` |
| **DB** | **Aurora 대신 EC2 1대 + PostgreSQL 직접 설치** (`modules/dev_tools/ec2_postgres`) | **Aurora PostgreSQL 클러스터**(Writer + Reader) **+ RDS Proxy** |
| DB 삭제 보호 | 없음 (테스트 편의) | `deletion_protection=true`, 삭제 시 최종 스냅샷 남김 |
| Valkey 구성 | 단일 노드 (`replica_count=0`) | Primary + Replica (`replica_count=1`) |
| GitHub OIDC Provider | dev/prod 둘 다 생성 안 함 — 이 공유 계정에 이미 있는(우리 프로젝트와 무관한) Provider를 데이터소스로 조회만 (2026-08-20 확인) | 위와 동일 |
| tfstate | `book-eating-lion-tfstate-dev` | `book-eating-lion-tfstate-prod` (완전 별도 상태) |

**DB를 다르게 쓰는 이유:** dev는 상시 켜두는 환경인데 Aurora(Multi-AZ, Serverless v2도 최소 0.5 ACU부터 시간당 과금)를 계속 띄워두기엔 비용이 안 맞습니다. 그래서 dev만 EC2 한 대에 PostgreSQL을 직접 깔아 비용을 줄이고, 나머지 EKS/네트워크 구조는 prod와 동일하게 유지해 실서비스 조건을 최대한 재현합니다. 두 모듈의 출력값 이름을 동일하게 맞춰서 `02-runtime`은 dev/prod 분기 없이 같은 SSM 키로 DB endpoint를 읽습니다.

**도메인(`ajttk.com`) 관련 참고 (2026-08-20 확정):** 이 도메인은 계정 소유자가 Route53 Domains로 이미 등록해둔 실제 도메인입니다. apex(`ajttk.com`)와 `api`/`grafana` 서브도메인은 예전 프로젝트가 쓰던 레코드라 이 프로젝트는 건드리지 않고, dev/prod 각각 `dev.ajttk.com`/`book.ajttk.com` 서브도메인만 새로 씁니다. 부모 Zone에 대한 NS 위임 레코드는 콘솔에서 수동으로 추가하지 않고 `modules/base/dns_zone`의 `aws_route53_record.delegation` 리소스가 `terraform apply` 한 번으로 자동으로 만듭니다(`var.parent_zone_domain = "ajttk.com"`, dev/prod 둘 다 이 모듈을 재사용).

## 3. 공통 원칙

- AWS 리전은 항상 **`ap-northeast-2`**(서울)만 씁니다. 예외: CloudFront용 ACM 인증서/WAF WebACL은 AWS 제약상 `us-east-1`에서만 발급 가능해서 그 두 리소스만 provider alias로 `us-east-1`을 씁니다(§6 참고).
- Access Key, DB 비밀번호, 인증서, 토큰은 GitHub/Notion/발표자료/화면 캡처에 노출하지 않습니다. 이 프로젝트는 DB 마스터 비밀번호를 `manage_master_user_password = true`(Aurora) 또는 Secrets Manager(`ec2_postgres`)로 관리해 tfvars/state에 평문이 남지 않게 합니다.
- 데이터베이스(Aurora, dev의 EC2 PostgreSQL)는 Private Subnet에만 두고 외부에 직접 공개하지 않습니다. 접근은 App Subnet의 보안그룹(`app_security_group_id`)에서만 허용합니다.
- 비용이 크게 발생할 수 있는 리소스(NAT Gateway, Aurora Multi-AZ reader, EKS 노드, ALB/NLB, CloudFront)는 새로 만들거나 스펙을 올리기 전에 팀원과 확인합니다.
- Terraform state는 계층별로 완전히 분리돼 있습니다(00-base / 01-data / 02-runtime) — 한 계층을 apply해도 다른 계층 state에는 손대지 않습니다.

## 5. 태그 규칙

`provider "aws"`의 `default_tags`로 전체 리소스에 자동 적용됩니다. 6개 파일(`environments/{dev,prod}/{00-base,01-data,02-runtime}/provider.tf`)에 동일하게 설정돼 있습니다.

| Key | Value | 비고 |
| --- | --- | --- |
| Project | `lion` | 코스/계정 차원 프로젝트 식별자 (리소스 네이밍 접두사 `lion-team3`와는 별개) |
| Team | `Team3` | §1의 계정 공유 규칙 핵심 태그 |
| Owner | `likelion-cloud6-team3` | 팀원 개인 실명 대신 프로젝트/팀 식별자 사용 |
| Environment | `dev` 또는 `prod` | `var.environment` 값 그대로 |
| ManagedBy | `terraform` (Karpenter 노드는 `karpenter`) | |
| Layer | `base` / `data` / `runtime` | 어느 state 계층이 만들었는지 |

> Karpenter가 EC2 API로 직접 만드는 노드(`EC2NodeClass`)는 `default_tags`를 상속받지 못해서 `modules/compute/karpenter/main.tf`에 위 표와 동일한 Project/Team/Owner를 별도로 명시했습니다.

## 6. 리전 예외 — `us-east-1` provider alias

CloudFront는 `us-east-1`에서 발급된 ACM 인증서와 `CLOUDFRONT` 스코프 WAF만 받을 수 있습니다(AWS 고정 제약). 그래서 `00-base`의 `acm_cert`, `waf` 두 모듈만 `providers = { aws = aws.us_east_1 }`로 호출합니다. 나머지 모든 리소스는 `ap-northeast-2`입니다.

## 7. 배포 절차 (Terraform 배포 런북)

### 7.1 사전 준비

- [ ] `aws sts get-caller-identity`로 자격 증명 확인 (리전: `ap-northeast-2`)
- [ ] Terraform `>= 1.8.0` 설치 확인
- [ ] **State 백엔드가 미리 존재해야 함** — `book-eating-lion-tfstate-{env}` S3 버킷과 `book-eating-lion-tflock-{env}` DynamoDB 테이블(dev/prod 각각). `terraform/bootstrap`이 이 둘을 만드는 코드다 — 계정에 아직 없으면(최초 1회) `cd terraform/bootstrap && terraform init && terraform apply` 로 먼저 만들어야 `environments/*` 쪽 `terraform init`이 된다. 이미 있으면 생략. 자세한 건 `TERRAFORM_STRUCTURE.md` §5.1/§6.1 참고.
- [ ] `terraform.tfvars`의 TODO 표시된 placeholder 값(도메인, S3 버킷명, 알림 이메일 등) 실제 값으로 교체 확인
- [ ] **(prod를 처음 배포하는 경우 필수) `./scripts/sync-github-config.sh prod`를 실행하기 전에, 지금 GitHub Variables가 dev 값(예: `AURORA_ENDPOINT`가 dev EC2 PostgreSQL의 IP/DNS)으로 채워져 있는 건 아닌지 `gh variable list`로 먼저 확인할 것.** `main-cd.yml`은 GitHub Environments가 아니라 레포 레벨 Variables/Secrets 하나만 쓰므로(§7.6 참고), dev용 값이 남아있는 상태로 prod Main CD를 돌리면 prod 서비스가 dev의 DB/Redis/큐를 그대로 바라보게 됩니다 — 배포는 "성공"하는데 실제로는 dev 데이터를 건드리는 사고로 이어질 수 있음.

### 7.2 환경 간 순서 — 없음 (dev/prod 독립적으로 apply 가능)

GitHub OIDC Provider(`aws_iam_openid_connect_provider`)는 AWS 계정당 URL 하나에 유일한 전역 리소스라, 원래는 "prod가 생성하고 dev는 조회만" 하는 모델을 쓰려 했습니다. 그런데 이 계정은 여러 팀이 공유하고 있고, 이미 (우리 프로젝트와 무관한) GitHub OIDC Provider가 그 URL에 존재합니다(2026-08-20 확인, 2025-12-23 생성). 그래서 **dev/prod 둘 다 `create_oidc_provider = false`**로 두고 기존 Provider를 데이터소스로 조회만 합니다. 결과적으로 dev/prod 사이에 apply 순서 의존성이 없습니다 — 각 환경은 §7.3의 계층 순서(00-base → 01-data → 02-runtime)만 지키면 됩니다.

### 7.3 계층 순서 (환경 하나 기준: `dev` 또는 `prod`)

```
00-base → 01-data → 02-runtime
```

각 계층은 상위 계층의 출력을 SSM Parameter Store로 조회하므로 반드시 이 순서로 apply해야 합니다(`docs/개발 문서/TERRAFORM_STRUCTURE.md` §4). `{env}`를 `dev` 또는 `prod`로 바꿔서 그대로 실행합니다.

```bash
# 0. State 백엔드 부트스트랩 — book-eating-lion-tfstate-{env} S3 버킷과
#    book-eating-lion-tflock-{env} DynamoDB 테이블이 계정에 이미 있으면 생략.
#    없으면(최초 1회, 또는 실수로 콘솔에서 지워진 뒤 — 자세한 경위는
#    docs/개발 문서/TERRAFORM_STRUCTURE.md §6.1 참고) 아래 계층들의
#    terraform init이 전부 "S3 bucket ... does not exist"로 실패하니
#    반드시 먼저 실행할 것.
cd terraform/bootstrap
terraform init
terraform plan -out=tfplan
terraform apply tfplan
cd ../..

# 1. Base 계층 (VPC, 서브넷, ECR, S3, Route53, ACM, WAF, SNS, GitHub OIDC)
cd terraform/environments/{env}/00-base
terraform init
terraform plan -out=tfplan
terraform apply tfplan

# 2. Data 계층 (dev: EC2 PostgreSQL / prod: Aurora, RDS Proxy, Valkey, Cognito)
cd ../01-data
terraform init
terraform plan -out=tfplan
terraform apply tfplan

# 3. Runtime 계층 (EKS → Karpenter → ALB Controller → CloudFront/AI IRSA)
cd ../02-runtime
terraform init
# 3-1. 클러스터부터 먼저 생성 — Karpenter/ALB Controller의 kubernetes/helm provider가
#      인증할 EKS 클러스터가 아직 없으면 이 단계에서 provider 초기화 자체가 실패한다.
terraform apply -target=module.eks_cluster
# 3-2. Karpenter Helm 차트(EC2NodeClass/NodePool CRD를 여기서 설치함)도 따로 먼저
#      올려야 한다 - CRD가 없는 상태에서 그 CRD를 쓰는 kubernetes_manifest 리소스를
#      plan하면 "no matches for kind EC2NodeClass"로 실패한다(2026-08-20 실제로 겪음).
terraform apply -target=module.karpenter.helm_release.karpenter
# 3-3. 나머지(Karpenter의 EC2NodeClass/NodePool, ALB Controller, edge_routing, AI 서비스 IAM) 적용
terraform plan -out=tfplan
terraform apply tfplan
```

> **왜 `plan -out` 후 사람이 확인하고 `apply tfplan`을 쓰는가:** `00-base`/`01-data`는 위험 등급 **Critical**입니다(계층별 위험도 매트릭스는 `docs/개발 문서/TERRAFORM_STRUCTURE.md` §1 참고). `-auto-approve`는 쓰지 않고, diff를 사람이 읽은 뒤 승인하는 2단계를 항상 거칩니다. `02-runtime`도 신규 인프라를 처음 세울 때는 동일 절차를 따르되, 이후 반복 배포(서비스 라우트 추가 등)부터는 팀 판단에 따라 CI로 자동화해도 됩니다.
>
> **`admin_principal_arns`(eks_cluster 모듈) 관련 주의:** 클러스터를 실제로 만든(3-1을 실행한) 사람은 `access_config.bootstrap_cluster_creator_admin_permissions=true`로 AWS가 자동으로 kubectl 관리자 권한을 줍니다. 그 사람을 `admin_principal_arns`에 또 넣으면 `aws_eks_access_entry`가 중복 생성을 시도해 `ResourceInUseException`(409)로 실패합니다 — 이 변수는 클러스터를 "만들지 않은" 다른 팀원/역할에게 나중에 권한을 추가로 줄 때만 씁니다.
>
> **`helm_release`가 `Error: cannot re-use a name that is still in use`로 실패하면:** `apply`가 Ctrl+C나 타임아웃으로 중간에 끊기면(Helm의 기본 `wait=true`가 5분 넘게 걸릴 때 특히) Helm 릴리스가 클러스터에 `pending-install` 상태로 멈춰 남는데, Terraform state엔 그 리소스가 기록 안 됩니다. 다음 apply가 "새로 만들려는데 그 이름 이미 있음"으로 막힙니다(2026-08-20 karpenter/ingress-nginx 둘 다 실제로 겪음). 해결: `helm list -n {namespace}`로 `pending-install` 상태 확인 → `helm uninstall {release} -n {namespace}`로 지우기 → `terraform plan`/`apply` 재시도. CRD는 Helm이 기본적으로 안 지우니 그대로 남아있어 다시 만들어도 안전합니다.
>
> **Karpenter 노드가 안 뜨거나 떠도 앱이 DB에 못 붙으면:** 3단계(전체 plan/apply)까지 다 끝냈는데도 Karpenter 노드가 `Registered=Unknown`에서 안 넘어가거나, 노드는 붙었는데 앱이 DB/Redis 연결에 실패하면 §7.7 ⑤⑥⑦을 먼저 볼 것 — EKS Access Entry, `ec2:CreateTags` IAM 권한, `app_security_group_id` 배선이 전부 코드에 이미 반영돼 있어야 정상 동작합니다(2026-08-21 이후 커밋 기준). 이미 떠 있는 Karpenter 노드는 EC2NodeClass가 바뀌어도 소급 적용되지 않으니, 관련 수정을 반영한 뒤에는 `kubectl get nodeclaims`로 기존 노드를 확인하고 `kubectl delete nodeclaim {name}`으로 지워서 새 스펙으로 재생성시킬 것.

### 7.4 자원 정리 및 삭제 순서 (배포 역순)

```bash
cd terraform/environments/{env}/02-runtime && terraform plan -destroy -out=destroy.tfplan && terraform apply destroy.tfplan
cd ../01-data                                && terraform plan -destroy -out=destroy.tfplan && terraform apply destroy.tfplan
cd ../00-base                                && terraform plan -destroy -out=destroy.tfplan && terraform apply destroy.tfplan
```

> `01-data`는 Aurora/Valkey 등 영속 데이터를 담은 Critical 계층이라 삭제 전 반드시 `plan -destroy`로 무엇이 지워지는지 사람이 먼저 확인합니다. dev처럼 데이터 유실이 문제되지 않는 환경에서만 팀 판단으로 `-auto-approve`를 써도 됩니다. dev/prod는 서로 독립적이라(§7.2) 어느 쪽부터 삭제해도 상관없습니다.

### 7.5 S3 Vectors 수동 생성 가이드 (Terraform 미지원 임시 조치)

`modules/data/ai_pipeline`은 벡터 버킷/인덱스 2개(추천 도서용, 구매도서 RAG 인용용)를 만들어야 하는데, `hashicorp/aws` provider(현재 고정 버전 5.100.0)에 `s3vectors_*` 리소스 타입 자체가 없어서 Terraform으로 못 만듭니다(2025년 말 출시된 신규 서비스라 provider가 아직 못 따라감 — provider 바이너리를 직접 열어 `s3vectors` 문자열을 검색해도 하나도 안 나옴, 2026-08-20 확인). 그래서 이 벡터 버킷/인덱스가 당장 필요하면 아래처럼 **AWS CLI로 수동 생성**해야 합니다(`aws-cli >= 2.x`는 `s3vectors` 명령어 그룹을 이미 지원함). `01-data`까지 apply한 뒤, `02-runtime`의 AI 서비스 IAM 권한을 완성하려면 이 단계를 거쳐야 합니다.

#### 7.5.1 만들 것

- 벡터 버킷 1개: `lion-team3-{env}-vectors`
- 인덱스 2개(같은 버킷 안):
  - `recommendation` — 추천 도서 인덱스 (신간 등록 이벤트로 비동기 색인)
  - `purchased-book-rag` — 구매도서 RAG 인용 인덱스 (구매한 책 본문만 검색 대상)

#### 7.5.2 생성 명령어 (dev 예시, `{env}`만 바꾸면 prod도 동일)

```bash
# 1. 벡터 버킷
aws s3vectors create-vector-bucket \
  --vector-bucket-name lion-team3-dev-vectors \
  --region ap-northeast-2

# 2. 추천 도서 인덱스
aws s3vectors create-index \
  --vector-bucket-name lion-team3-dev-vectors \
  --index-name recommendation \
  --data-type float32 \
  --dimension 1024 \
  --distance-metric cosine \
  --region ap-northeast-2

# 3. 구매도서 RAG 인용 인덱스
aws s3vectors create-index \
  --vector-bucket-name lion-team3-dev-vectors \
  --index-name purchased-book-rag \
  --data-type float32 \
  --dimension 1024 \
  --distance-metric cosine \
  --region ap-northeast-2
```

> `--dimension 1024`는 Bedrock Titan Embeddings V2(`amazon.titan-embed-text-v2:0`)의 기본 출력 차원입니다. 앱이 Bedrock 호출 시 `dimensions` 파라미터를 256/512로 줄여서 쓰면 여기도 반드시 그 값과 똑같이 맞춰야 합니다 — 다르면 인덱스에 벡터를 못 넣습니다.
>
> `--distance-metric`은 `cosine`/`euclidean` 중 선택 — 텍스트 임베딩 유사도 검색엔 일반적으로 `cosine`을 씁니다.

#### 7.5.3 생성 후 ARN 확인 (Terraform에 수동으로 넣어야 함)

```bash
aws s3vectors get-vector-bucket --vector-bucket-name lion-team3-dev-vectors --query 'vectorBucket.vectorBucketArn'
aws s3vectors get-index --vector-bucket-name lion-team3-dev-vectors --index-name recommendation --query 'index.indexArn'
aws s3vectors get-index --vector-bucket-name lion-team3-dev-vectors --index-name purchased-book-rag --query 'index.indexArn'
```

`ai_service_iam` 모듈 호출부(`environments/{env}/02-runtime/main.tf`)의 `recommendation_index_arn`/`purchased_book_rag_index_arn`이 지금 `null`로 고정돼 있는데, 이 ARN들로 바꿔주면 IAM 정책의 `S3VectorsReadWrite` statement가 자동으로 활성화됩니다(모듈 코드에 이미 `dynamic "statement"`로 조건부 처리돼 있음 — 코드 자체는 이미 준비돼 있고 값만 채우면 됨).

#### 7.5.4 나중에 provider가 지원하면

`hashicorp/aws` provider가 `aws_s3vectors_bucket`/`aws_s3vectors_index` 같은 리소스 타입을 추가하면, 수동으로 만든 이 버킷/인덱스를 `terraform import`로 가져와서 그때부터 Terraform이 관리하게 전환하는 걸 권장합니다 — 다시 만들 필요 없이 기존 벡터 데이터를 그대로 유지한 채 IaC로 편입 가능합니다.

### 7.6 GitHub Actions Variables/Secrets 자동 등록

`main-cd.yml`이 요구하는 Variables(인프라/인증·네트워크/도메인·스토리지·ECR·DB·캐시/큐 등 18개 필수 + 5개 선택) / Secrets(DB 계정 8개 + Cognito + 카카오페이 등 11개)를 AWS 콘솔에서 하나씩 찾아 복사-붙여넣기 하는 게 번거로워서, `scripts/sync-github-config.sh`로 자동화했습니다.

**용도:** SSM Parameter Store, ECR, Secrets Manager, CloudFront 등에서 값을 직접 조회해 `gh variable set`/`gh secret set`으로 등록합니다. DB 비밀번호 같은 민감값은 화면에 출력하지 않고 바로 `gh secret set`으로 전달합니다.

**사용법:**

```bash
./scripts/sync-github-config.sh dev
./scripts/sync-github-config.sh prod
```

**전제조건:** `gh auth status`로 로그인 확인, `aws sts get-caller-identity`로 자격 증명 확인, 대상 환경의 `00-base`/`01-data`/`02-runtime`이 이미 apply돼 있을 것(SSM 파라미터가 없으면 그 값은 SKIP으로 표시하고 넘어갑니다).

**자동으로 못 채우는 값(SKIP으로 표시됨)과 이유:**

| 값 | SKIP되는 이유 |
| --- | --- |
| `AI_VECTOR_BUCKET` | S3 Vectors가 아직 없으면(§7.5 가이드를 먼저 실행) |
| `AI_DB_NAME` | Terraform엔 DB가 하나(`bookdb`)뿐이라 별도 이름을 알 수 없음 |
| `AWS_COGNITO_CLIENT_SECRET` | Cognito 클라이언트가 `generate_secret=false`(공개 클라이언트)라 시크릿 자체가 없음 |
| `KAKAOPAY_SECRET_KEY` | AWS 밖의 값(카카오 개발자센터에서 발급) — `gh secret set KAKAOPAY_SECRET_KEY`로 직접 등록할 것 |

> **주의:** `main-cd.yml`은 GitHub Environments를 쓰지 않고 레포 레벨 Variables/Secrets 하나만 참조합니다. 그래서 이 스크립트를 `dev`로 한 번 돌리고 나중에 `prod`로 다시 돌리면 값이 prod 것으로 덮어써집니다. dev/prod를 동시에 운영하려면 워크플로에 GitHub Environments를 도입하는 별도 작업이 필요합니다(현재 범위 밖).

### 7.7 CI/CD 첫 실행 트러블슈팅

`workflow_dispatch`로 `main-cd.yml`을 처음 돌렸을 때(2026-08-20) 실제로 겪은 문제 2가지. 둘 다 코드에 반영 완료.

**① `Not authorized to perform sts:AssumeRoleWithWebIdentity`**

GitHub이 OIDC 토큰의 `sub` claim 기본 형식을 리포지킹(repojacking) 방지 목적으로 바꿨습니다.

```
예전: repo:OWNER/REPO:ref:refs/heads/BRANCH
현재: repo:OWNER@ownerId/REPO@repoId:ref:refs/heads/BRANCH   (예: repo:Burrun@127071470/book-eating-lion-dev@1318056441:ref:refs/heads/dev)
```

`github_oidc` 모듈의 trust policy가 옛날 형식(`repo:OWNER/REPO:*`)만 매치하도록 돼 있어서 전부 `AccessDenied`. CloudTrail의 `AssumeRoleWithWebIdentity` 이벤트(`userIdentity.principalId`)로 실제 `sub` 값을 확인하고 원인을 특정했습니다. `repo:${github_org}@*/${github_repo}@*:*`처럼 ID 부분을 와일드카드로 열어서 해결(`terraform/modules/base/github_oidc/main.tf`).

**② OIDC는 통과했는데 S3/EKS 권한이 부족함**

- `Sync to Amazon S3`: `s3:ListBucket` `AccessDenied` — CI 역할(`github_actions`)에 S3 권한 자체가 없었음. `frontend_bucket_arn`/`media_bucket_arn`을 `github_oidc` 모듈에 넘겨 `s3:ListBucket`(버킷)/`GetObject`·`PutObject`·`DeleteObject`(객체)와 `cloudfront:CreateInvalidation`을 추가.
- `kubectl apply` (`01-namespace.yaml`): `namespaces is forbidden` — CI 역할의 EKS access policy가 `AmazonEKSAdminPolicy`(K8s 내장 `admin` ClusterRole)였는데, 이건 네임스페이스 **안**의 리소스만 관리하고 Namespace 객체 자체 같은 cluster-scoped 리소스는 못 만듭니다. `admin_principal_arns`(사람)와 같은 `AmazonEKSClusterAdminPolicy`(`cluster-admin` 매핑)로 교체(`terraform/modules/compute/eks_cluster/main.tf`).

두 경우 다 `00-base`(①②의 S3 부분) / `02-runtime`(②의 EKS 부분) 재apply로 반영됩니다 — 리소스 재생성 없이 IAM policy/access entry만 update-in-place.

**③ ECR 리포지토리 이름에 레지스트리 주소가 두 번 붙음**

`k8s/*/deployment*.yaml`과 `main-cd.yml`의 `Build & push image` 스텝은 둘 다 `${ECR_REGISTRY}/${ECR_*_REPO}` 형태로 직접 조합합니다 — 즉 `ECR_CATALOG_REPO` 같은 Variable엔 **레지스트리 주소 없는 순수 리포 이름**(`lion-team3-dev/catalog`)만 들어가야 합니다. `sync-github-config.sh`가 처음엔 레지스트리 주소까지 합친 전체 URI를 넣도록 돼 있어서, 조합 시 레지스트리가 두 번 붙은 잘못된 이미지 이름(`...amazonaws.com/...amazonaws.com/lion-team3-dev/catalog`)이 됐고, 그 이름의 리포지토리는 당연히 존재하지 않아 `ecr:InitiateLayerUpload`가 (권한이 아니라 대상 자체가 없어서) `denied`로 실패했습니다(2026-08-20 실제로 겪음). 스크립트를 순수 리포 이름만 넣도록 고쳤습니다 — 이미 등록된 값이 있다면 `./scripts/sync-github-config.sh {env}` 재실행으로 정정됩니다.

**④ (해결됨 — 옵션 B 적용) 파드가 `exec format error`로 CrashLoopBackOff**

`order`/`member` 서비스가 ECR push까지는 성공하고 `kubectl apply`도 성공하는데, 파드가 계속 죽습니다:

```
exec /opt/java/openjdk/bin/java: exec format error
```

**원인**: CPU 아키텍처 불일치. Karpenter `NodePool`(`terraform/modules/compute/karpenter/main.tf`)이 `kubernetes.io/arch: arm64`만 요구하도록 돼 있어(비용 절감 목적) 클러스터 노드가 전부 Graviton(arm64)인데, `main-cd.yml`의 `docker build`는 GitHub `ubuntu-latest` 러너(amd64)에서 `--platform` 지정 없이 빌드해서 이미지가 amd64로 나옵니다. amd64 바이너리를 arm64 커널에 올리니 즉시 죽는 것 — `kubectl -n lion-app get nodes -L kubernetes.io/arch`로 arm64 확인, `kubectl logs --previous`로 확인함(2026-08-20).

**옵션 (다음에 하나 골라서 진행할 것):**

| 옵션 | 방법 | 장점 | 단점 |
| --- | --- | --- | --- |
| A. CI를 arm64로 빌드 | `docker/setup-qemu-action` + `docker/setup-buildx-action` 추가, `docker buildx build --platform linux/arm64`로 변경. Dockerfile의 builder 스테이지는 `FROM --platform=$BUILDPLATFORM ...`로 고정해 QEMU 에뮬레이션 없이 네이티브(amd64)로 컴파일하고, 최종 JRE 스테이지만 arm64로 크로스타겟(자바 바이트코드는 아키텍처 무관이라 가능) | Graviton 비용 절감 유지, 노드/Karpenter 변경 없음 | 서비스 4개 Dockerfile 전부 수정 + 워크플로 buildx 설정 필요 |
| B. NodePool을 amd64로 되돌림 | `karpenter/main.tf`의 `kubernetes.io/arch` 값을 `amd64`로 변경 후 02-runtime재apply | 코드 변경 최소(한 줄), CI는 이미 amd64로 잘 만들고 있어 즉시 해결 | Graviton 대비 온디맨드/스팟 단가가 더 비쌈(비용 절감 포기) |
| C. GitHub arm64 호스팅 러너 사용 | 빌드 잡의 `runs-on`을 arm64 러너 라벨로 변경 | QEMU 에뮬레이션 없이 네이티브 arm64 빌드, Dockerfile 수정 불필요 | 이 리포의 GitHub 플랜/티어가 arm64 호스팅 러너를 지원하는지 확인 필요(비공개 리포는 유료 플랜 요구할 수 있음) |

최종적으로 **B(NodePool을 amd64로 되돌림)**를 적용했습니다 — `modules/compute/karpenter/main.tf`의 NodePool 요구사항이 `kubernetes.io/arch: amd64`로 고정돼 있습니다. Graviton으로 다시 전환하려면 이 표의 A 또는 C를 먼저 적용한 뒤 되돌릴 것.

**⑤ Karpenter가 EC2는 띄우는데 노드로 영영 등록 안 됨 (`Launched=True`, `Registered=Unknown`에서 멈춤)**

클러스터가 `authenticationMode = "API"`(aws-auth ConfigMap 없이 EKS Access Entry만 사용)인데, Karpenter가 만드는 노드의 IAM Role(`lion-team3-{env}-karpenter-node`)에 Access Entry가 없었습니다. EKS Managed NodeGroup(시스템 노드그룹)은 EKS가 알아서 등록해주지만, Karpenter가 띄우는 셀프 관리 EC2는 그렇지 않습니다 — `type = "EC2_LINUX"` Access Entry를 직접 만들어야 합니다. `modules/compute/karpenter/main.tf`에 `aws_eks_access_entry.karpenter_node` 리소스로 추가했습니다(2026-08-21).

**⑥ Karpenter 컨트롤러가 launch template을 만들다 `ec2:CreateTags` UnauthorizedOperation**

Karpenter 공식 최소 IAM 정책은 "이미 `karpenter.sh/nodepool` 태그가 붙은 리소스"에 대한 `CreateTags`(`AllowScopedInstanceManagement`)와, "지금 막 생성되는 리소스"에 대한 `CreateTags`(`AllowScopedResourceCreationTagging`, `ec2:CreateAction` 조건으로 스코프)를 **별도 statement**로 나눠서 요구하는데, 후자가 빠져 있었습니다. launch template을 만들면서 동시에 태그를 붙이려는 요청은 "아직 그 태그가 없는" 리소스에 대한 요청이라 전자로는 커버가 안 됩니다(닭-달걀 문제). `modules/compute/karpenter/main.tf`에 `AllowScopedResourceCreationTagging` statement를 추가했습니다(2026-08-21).

**⑦ Karpenter 노드에서 앱이 DB/Redis에 연결 못 함 (Hibernate `Unable to determine Dialect`, connection timeout)**

`modules/base/vpc`가 만드는 `app_security_group_id`(EKS 노드/Pod 공용 SG — Aurora/RDS Proxy/Valkey/EC2 PostgreSQL이 전부 "이 SG에서 오는 트래픽만 허용"하는 기준)를, 정작 노드에 아무도 안 붙이고 있었습니다. `eks_cluster`의 시스템 노드그룹도, `karpenter`의 EC2NodeClass도 EKS 클러스터 기본 SG(`cluster_security_group_id`)만 썼습니다 — 이러면 노드↔control plane 통신은 되지만 데이터 계층 접근은 전부 막힙니다. `karpenter` 모듈의 `securityGroupSelectorTerms`에 `app_security_group_id`를 추가로 붙이도록 고쳤고(`node_security_group_id`, `app_security_group_id` 둘 다 attach — selectorTerms는 나열하면 매칭되는 SG가 전부 붙는 OR 매칭), `environments/{dev,prod}/02-runtime/main.tf`가 SSM(`/{env}/network/app_security_group_id`)에서 값을 읽어 전달하도록 배선했습니다(2026-08-21). **이미 떠 있던 노드에는 소급 적용 안 되니, 이 변경을 반영한 뒤에는 기존 Karpenter 노드(`kubectl delete nodeclaim`)를 지워서 새 SG로 재생성시켜야 합니다** — 시스템 노드그룹(managed)은 아직 이 SG를 안 쓰는데, CoreDNS/Karpenter 컨트롤러만 도는 용도라 지금 당장은 문제없지만 그 노드에도 뭔가 DB 접근이 필요해지면 같은 원인으로 막힙니다.

**⑧ `ExternalName` Service에 IP를 넣으면 DNS가 `NXDOMAIN`**

`k8s/base/04-db.yaml`의 `db-primary-service`/`db-reader-service`는 `type: ExternalName`인데, 이 타입은 **DNS 호스트네임만 허용**합니다(내부적으로 CNAME 레코드를 만드는 것과 같음) — IP 주소를 넣으면 생성은 되지만 CoreDNS가 못 풀어서 `UnknownHostException`/`NXDOMAIN`이 납니다. dev는 Aurora 대신 EC2 PostgreSQL을 쓰는데, `AURORA_ENDPOINT`/`AURORA_READER_ENDPOINT` GitHub Variable에 그 EC2의 **프라이빗 IP**가 그대로 들어가 있었던 게 원인이었습니다. EC2의 **프라이빗 DNS 이름**(`ip-10-13-10-42.ap-northeast-2.compute.internal` 형식 — VPC의 `enableDnsHostnames=true`가 켜져 있어야 존재함, 이 프로젝트는 이미 켜져 있음)으로 바꿔서 해결했습니다. `k8s/base/04-db.yaml`의 기존 주석("EC2 Postgres로 전환하면 `${TEST_DB_ENDPOINT}`로 바꾸거나...")은 `TEST_DB_ENDPOINT`도 결국 IP값이면 똑같이 깨진다는 걸 언급 안 하고 있으니, **EC2 IP를 여기 쓸 일이 있으면 반드시 프라이빗 DNS 이름으로 변환해서 쓸 것.** prod는 실제 Aurora 클러스터 엔드포인트(원래부터 DNS 이름 형식)를 쓰므로 이 문제와 무관합니다.

**⑨ `SQS_INGEST_QUEUE_URL`이 통째로 배선 누락 (Spring 순환 참조 에러)**

`ai_pipeline` 모듈이 `purchase_channel_url`(SQS 큐 URL) output은 만들면서 `ingest_channel_url`은 안 만들고 있었습니다(ARN만 있었음) — 그래서 SSM 파라미터도, `sync-github-config.sh`의 등록 대상도, `main-cd.yml`의 env/VARS도 전부 이 값이 빠져 있었습니다. `k8s/catalog`, `k8s/ai`의 ConfigMap이 `${SQS_INGEST_QUEUE_URL}`을 참조하는데 치환이 안 돼 리터럴 문자열이 그대로 들어갔고, Spring이 이걸 자기 자신을 가리키는 플레이스홀더로 오인해 `Circular placeholder reference`로 기동 실패했습니다. `ai_pipeline` 모듈에 `ingest_channel_url` output 추가, `environments/{dev,prod}/01-data/main.tf`에 SSM 파라미터(`/{env}/ai/ingest_channel_url`) 추가, `sync-github-config.sh`와 `main-cd.yml`에 배선을 추가했습니다(2026-08-21).

**⑩ `-target`으로 일부만 apply하면 경고 없이 리소스가 통째로 빠질 수 있음 — 배포 실패 시 진단 순서**

⑤⑥⑦⑨는 전부 최초 apply 때는 안 드러나다가, `-target`으로 좁혀서 재시도하거나 여러 번 부분 apply를 반복하는 과정에서 하나씩 나타났습니다. `terraform apply -target=...`은 그 리소스가 **명시적으로 의존하는** 것만 같이 적용하고, 같은 모듈 안에 있어도 의존 관계가 없는 리소스(IAM 정책, Access Entry 등)는 조용히 건너뜁니다 — "Applied changes may be incomplete" 경고가 뜨긴 하지만 정확히 뭐가 빠졌는지는 알려주지 않습니다. **§7.3의 3단계(전체 `plan`/`apply`)를 반드시 끝까지 실행해서 이 경고가 더 이상 안 뜨는 상태로 만들 것.** 또한 `main-cd.yml`의 `Rollback on failure` 스텝은 `Wait for rollout` 타임아웃(=실패로 간주) 시 자동으로 `kubectl rollout undo`를 실행해서 **더 예전(더 고장난) 이미지로 되돌립니다** — 새 이미지가 실제로 뭘 하다 죽었는지 확인하려면 롤백되기 전에(타임아웃 600초 이내) `kubectl logs --previous`로 봐야 하고, 이미 롤백됐다면 `kubectl set image deployment/{name} {container}={새 이미지}`로 직접 재배포해서 로그를 다시 확인하는 게 빠릅니다. 겪은 순서대로 원인이 겹쳐 있었다는 점도 참고할 것 — 하나 고치고 재배포해도 다음 계층의 문제(IAM → 네트워크 → DNS → 환경변수)가 순서대로 드러났습니다.

### 7.7.1 2026-08-21 "1:1 채팅이 안 된다" 장애 대응 — 연쇄로 드러난 배포 차단 이슈 5건

1:1 채팅 상담 기능 리포트를 계기로 dev 클러스터를 점검하다가, 계층이 다른 배포 차단 버그가 순서대로 드러났습니다(⑦⑨가 겪은 것과 같은 패턴 — 하나 고치면 다음 계층이 드러남). 두 명이 동시에 다른 문제를 나눠서 고쳤고, 문서화 시점(같은 날) 기준 상태는 각 항목에 표기했습니다.

**⑪ (해결, PR #64) `CHAT_ALLOWED_ORIGINS`가 CI 배선에서 통째로 빠져 채팅 WebSocket이 전부 거절됨**

`k8s/ai/configmap.yaml`의 `CHAT_ALLOWED_ORIGINS: "${CHAT_ALLOWED_ORIGINS}"`는 `/ws/ai/chat` 핸드셰이크의 유일한 Origin 방어선(`WebSocketConfig.setAllowedOriginPatterns` — WS는 preflight가 없어 Ingress CORS가 안 먹힘)인데, `main-cd.yml`의 `ai` 배포 스텝(env 블록과 envsubst VARS 목록 둘 다)에 이 변수가 아예 없었습니다. `envsubst`는 VARS 목록에 없는 `${VAR}`는 손대지 않으므로, 배포된 ConfigMap에 리터럴 문자열이 그대로 들어갔고 — 실제 브라우저 Origin과 맞을 리 없어 핸드셰이크가 항상 403으로 거절됐습니다(dev 클러스터에 배포된 ConfigMap 값으로 직접 확인). `FRONTEND_ORIGIN`과 값이 같아야 하므로 새 GH Variable 없이 재사용하도록 배선(PR #64, 병합됨).

**⑫ (해결) `AI_DB_NAME` GitHub Variable 미등록 + dev EC2 Postgres에 스키마가 하나도 없었음**

두 가지가 겹쳐서 `ai`/`member`/`order` 파드가 전부 DB 연결 단계에서 죽었습니다.

- `scripts/sync-github-config.sh`가 `AI_DB_NAME`을 "Terraform엔 DB 하나(bookdb)뿐이니 AI 전용 DB명이 따로 있으면 직접 등록하라"는 경고만 찍고 의도적으로 스킵했는데, 실제로 등록한 사람이 없었습니다. `main-cd.yml`의 `ai` 배포 스텝엔 `AI_VECTOR_BUCKET`/`EBOOK_S3_BUCKET`과 달리 이 값에 대한 필수값 가드(`exit 1`)가 없어 빈 값이어도 조용히 배포가 진행됐습니다. 결과: JDBC URL의 DB명이 빈 문자열이 되고, PostgreSQL은 dbname 미지정 시 접속 계정명으로 기본 처리하므로 `FATAL: database "bookadmin" does not exist`로 죽었습니다. `gh variable set AI_DB_NAME --body bookdb`로 등록해 해결.
- `db/postgres/00-init.sql`(스키마 4개 + 서비스 계정 4개 + 권한) ~ `04-ai_db.sql`(테이블 DDL)이 저장소엔 있는데, **dev/prod 실인프라에 적용된 적이 한 번도 없었습니다.** `terraform/modules/dev_tools/ec2_postgres/main.tf`의 `user_data`는 "스키마 적용은 배포 파이프라인 몫"이라고 주석으로 떠넘겨 놨는데, 어떤 CI 워크플로에도 이 SQL을 실행하는 스텝이 없었습니다 — 로컬 docker-compose만 Postgres 공식 이미지의 `/docker-entrypoint-initdb.d/` 최초-기동 컨벤션으로 자동 실행되고 dev/prod는 해당 없음. dev EC2 Postgres에 SSM Session Manager로 접속해 `00-init.sql`부터 순서대로 수동 실행해서 해결(SQL 자체는 `IF NOT EXISTS` 가드가 있어 재실행 안전). **CI에 스키마 적용 스텝을 아예 추가할지, 계속 수동 런북으로 둘지는 아직 미결정 — 다음에 결정할 것.**

두 항목 해결 후 `catalog`/`member`/`order`는 재배포 없이도(⑬의 taint 적용분과 합쳐) 전부 `1/1 Running`, 재시작 0회로 안정화된 것을 직접 확인했습니다.

**⑬ (해결, PR #62/#63/#65) 그 다음 계층 — 노드 스케줄링, Redisson TLS, IRSA**

DB/스키마가 뚫린 뒤 순서대로 드러난 문제 3건, 전부 병합 완료:

- **시스템 노드그룹 오배치** (PR #62): EKS 관리형 "system" 노드그룹(t3.medium, CoreDNS/Karpenter 컨트롤러용)에 taint가 없어서 `ai`/`member`/`order` 파드가 여기로도 스케줄링될 수 있었는데, 이 노드그룹엔 `app_security_group_id`가 안 붙어 있어(⑦의 Karpenter EC2NodeClass 수정이 이 노드그룹까진 커버 안 함) DB/Redis 연결이 막혔습니다. taint 추가 + 앱 워크로드에 Karpenter 노드용 toleration을 배선.
- **order-api Redisson이 TLS 없이 ElastiCache에 접속** (PR #63): Spring Data Redis(Lettuce, catalog/ai가 씀)는 `spring.data.redis.ssl.enabled`를 자동으로 따라가지만, 재고 차감 분산 락 전용인 Redisson(`RedissonConfig`, order 전용)은 별도 클라이언트라 이 값을 안 읽고 `"redis://"`(평문)로 하드코딩돼 있었습니다. Valkey가 `transit_encryption_enabled=true`(TLS 강제)라 평문 연결의 PING이 응답 없이 타임아웃되며 기동이 영원히 멎었습니다 — 기존 `ssl.enabled` 프로퍼티를 재사용해 `rediss://` 스킴을 선택하도록 수정. *(배포된 JAR을 직접 까서 구버전 클래스가 들어있는 걸 확인하는 방식으로 "이미 코드엔 있는데 왜 재현되지"를 검증했습니다 — 배포 이미지가 이 수정보다 오래된 커밋이었을 뿐이었습니다.)*
- **ai-rag/ai-bot IRSA ServiceAccount 누락 + `AI_EPUB_BUCKET` 순환 참조 + member startupProbe 상한 부족** (PR #65): `ai_service_iam` 모듈이 IAM Role은 만들지만 그 Role을 참조하는 k8s `ServiceAccount`가 없어서 두 Deployment 모두 `default` SA로 뜨고, AWS SDK 자격증명 체인이 통째로 비어 `SdkClientException`으로 기동 즉시 죽었습니다 — `k8s/ai/serviceaccount.yaml` 신규 추가 + Role ARN을 SSM→GH Variable(`AI_SERVICE_IRSA_ARN`)→envsubst로 배선. 같은 PR에서 `AI_EPUB_BUCKET`의 ⑨와 동일한 패턴(CI에 없는 변수 참조로 리터럴 박힘, `EBOOK_S3_BUCKET` 재사용으로 수정)과, `member`만 `startupProbe.failureThreshold`가 60초로 남아있던 것(다른 서비스와 같은 180초로 통일)도 같이 고쳤습니다. prod의 `02-runtime`도 코드는 동일하게 고쳐뒀지만 **prod는 아직 미배포 — 처음 띄울 때 이 PR이 이미 반영된 상태여야 같은 문제를 안 겪습니다.**

**⑭ (미해결) Karpenter/시스템 노드 Role에 CloudWatch Logs·X-Ray 쓰기 권한 없음**

`lion-team3-dev-karpenter-node`/`lion-team3-dev-eks-node` Role 둘 다 Application Signals 로그 그룹/X-Ray 쓰기 권한이 없어서, OTel 사이드카가 파드 로그·트레이스를 CloudWatch로 못 보냅니다. 앱 자체의 기동/요청 처리는 안 막히지만(에러는 파드 로그엔 남음), CloudWatch 대시보드·X-Ray는 비어 보이니 "관측성 데이터가 왜 없지"로 헷갈리기 쉽습니다. IAM 정책에 `logs:PutLogEvents`/`xray:PutTraceSegments` 추가 필요.

**⑮ (미해결, 우선순위 검토 중) GitHub Actions Variables/Secrets가 레포 레벨 하나뿐 — dev/prod 전환마다 값이 서로 덮어씀**

`main-cd.yml`은 GitHub Environments를 안 쓰고 레포 레벨 Variables/Secrets 하나만 참조합니다(`scripts/sync-github-config.sh` 자체 주석에 명시). `./scripts/sync-github-config.sh dev`로 dev 값을 채운 뒤 나중에 `prod`로 다시 돌리면 `EKS_CLUSTER`/`AURORA_ENDPOINT`/`AWS_COGNITO_USER_POOL_ID`/`REDIS_HOST`처럼 두 환경이 다른 값을 쓰는 항목이 전부 prod 값으로 덮어써지고, dev를 다시 배포하려면 스크립트를 dev로 재실행해야 합니다. 배포 직전에 항상 대상 환경으로 스크립트를 재실행하는 수동 규율로만 지금은 막고 있습니다. **정석 해결책은 GitHub Environments(`dev`/`prod`) 도입 + 워크플로 job에 `environment:` 지정** — Variable/Secret이 환경별로 완전히 분리돼 전환 비용이 없어집니다. dev/prod를 나란히 놓고 비교 테스트(예: RDS Proxy 유무 비교)할 계획이라면 이 전환 비용이 매번 반복되니 우선순위를 올릴 만합니다. → 다음 작업으로 별도 브랜치에서 진행 예정.

## 8. 보안 원칙

- **보안그룹은 최소 권한**: DB(Aurora/EC2 PostgreSQL)·Valkey·RDS Proxy 보안그룹은 전부 `app_security_group_id`(EKS 노드/Pod 공용 SG)에서만 인바운드를 엽니다. `0.0.0.0/0`은 CloudFront/ALB의 80/443 등 정말 외부 공개가 필요한 곳에만 씁니다.
- **DB 비밀번호는 평문으로 두지 않음**: Aurora는 `manage_master_user_password = true`(AWS가 Secrets Manager에 자동 발급), dev의 EC2 PostgreSQL은 `random_password` + Secrets Manager를 쓰고 인스턴스가 부팅 시점에 직접 읽어옵니다. `user_data`/tfvars/state에 비밀번호 문자열을 절대 넣지 않습니다.
- **DB는 Private Subnet에만**: Aurora와 dev EC2 PostgreSQL 모두 Data 또는 App Subnet(Private)에 위치하고 Public IP가 없습니다. dev EC2 PostgreSQL은 SSH도 안 열고 SSM Session Manager로만 접속합니다.
- **CI/CD 권한은 최소 스코프**: GitHub Actions는 OIDC로 인증하고, 트러스트 정책의 `sub` 조건을 이 저장소(`Burrun/book-eating-lion-dev`, dev/prod가 공유하는 유일한 repo)로 제한합니다. EKS 배포 권한은 `aws_eks_access_entry`로 이 Role에만 명시적으로 부여합니다 — 단, `main-cd.yml`이 `k8s/base/03-secret.yaml`도 같이 적용하기 때문에 access policy는 `AmazonEKSAdminPolicy`를 씁니다(더 좁은 `AmazonEKSEditPolicy`는 secrets 리소스 권한이 빠져 있어 Secret apply가 깨짐 — 2026-08-20 확인). 진짜 최소권한화하려면 AWS 관리형 정책 대신 이 Role 전용 K8s ClusterRole을 따로 만들어야 하는데 아직 미구현.
- **CloudFront 뒤가 아니면 S3에 직접 접근 불가**: 프론트엔드/미디어 버킷은 CloudFront Origin Access Control(OAC)로만 접근을 허용하고 버킷을 퍼블릭으로 열지 않습니다.
- **저장 데이터 암호화**: Aurora는 `storage_encrypted = true`, S3 버킷 2개는 SSE(AES256)를 명시적으로 켭니다(둘 다 기본값이 꺼짐이라 빼먹기 쉬움).
- **EKS API 서버 접근 제한 가능**: `endpoint_public_access`는 켜져 있지만(GitHub-hosted runner의 IP 대역이 넓어 기본은 전체 허용) `public_access_cidrs` 변수로 좁힐 수 있습니다. self-hosted runner나 VPN을 쓰게 되면 이 값을 실제로 제한할 것.
- **dev EC2 PostgreSQL은 IMDSv2 강제**: `metadata_options.http_tokens = "required"`로 IMDSv1을 막습니다.

## 9. 프로젝트 종료 후 리소스 정리

기본 절차는 §7.4의 배포 역순 `terraform destroy`(`02-runtime` → `01-data` → `00-base`)입니다. 그것만으로 안 지워지거나 별도 확인이 필요한 항목들:

- [ ] S3 버킷(frontend/media) 내부 오브젝트를 먼저 비운다 — 안이 안 비어 있으면 `terraform destroy`가 실패함(버저닝이 켜져 있으면 버전까지 전부 삭제해야 함)
- [ ] ECR 레포에 남은 이미지 확인 — `image_tag_mutability=IMMUTABLE` + lifecycle policy(최근 30개 유지)라 오래된 태그는 자동 정리되지만, repo 자체를 지우려면 이미지가 안 남아있어야 함(필요시 force delete)
- [ ] Aurora 최종 스냅샷 확인 — prod는 `skip_final_snapshot=false`라 클러스터 삭제 시 스냅샷이 자동으로 남는다. 스냅샷도 비용이 발생하니 필요 없으면 별도로 지운다
- [ ] Secrets Manager 시크릿(Aurora master, EC2 PostgreSQL) — 삭제해도 기본 7~30일 복구 대기 기간 동안 과금되니, 필요 없으면 즉시 삭제(force delete) 검토
- [ ] CloudWatch Log Group 확인 — EKS control plane, Karpenter, `amazon-cloudwatch-observability` 애드온이 만드는 로그 그룹은 Terraform이 직접 관리하지 않아 클러스터를 지워도 자동으로 안 지워질 수 있음
- [ ] NAT Gateway / Elastic IP 재확인 — `00-base` destroy에 포함되지만, destroy가 중간에 실패해 멈추면 그대로 과금되는 대표 리소스라 꼭 다시 확인
- [ ] GitHub OIDC Provider는 dev/prod 둘 다 소유하지 않는 공유 계정 리소스라(§7.2) 우리가 지울 대상이 아님 — 삭제 순서 신경 안 써도 됨
- [ ] S3 Vectors 버킷/인덱스(§7.5로 수동 생성했다면) — Terraform이 모르는 리소스라 destroy에 안 걸림, `aws s3vectors delete-index`/`delete-vector-bucket`로 직접 정리
- [ ] Route53 Hosted Zone — 도메인을 계속 쓸 계획이면 Zone은 남기고 그 안의 레코드만 정리한다(Zone 자체를 지우면 네임서버가 바뀌어 재등록이 필요함)
- [ ] `terraform state list`로 각 계층(00-base/01-data/02-runtime)에 남은 리소스가 없는지 최종 확인
- [ ] 남아 있는 비용 발생 리소스 최종 확인 후 팀에 공유
