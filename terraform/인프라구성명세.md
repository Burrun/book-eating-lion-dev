# 팀 태그 · 리소스 사용 — 모든 팀원 필독

> ✅ 이 부분은 **계정을 옮겼든 아니든, 팀 프로젝트를 하는 모든 사람**에게 해당됩니다.
> 

## 🏷️ 가장 중요한 규칙: 리소스에 팀 태그 붙이기

리소스(EC2 등)를 만들 때 **반드시 팀 태그**를 붙여야 합니다.

- **키(Key):** `Team`
- **값(Value):** `team3`

### 태그를 붙이면

- ✅ 팀원끼리 같은 리소스를 함께 관리할 수 있습니다.
- ✅ 팀별 비용이 정확히 집계됩니다.
- ✅ 다른 팀이 우리 팀 리소스를 실수로 종료·삭제할 수 없습니다.

### 태그를 빠뜨리면

- ⚠️ **같은 팀원도** 그 리소스를 종료·삭제·정리할 수 없습니다.
- ⚠️ 비용 집계에서 누락됩니다.

> 리소스를 만들 때 태그 넣는 습관을 처음부터 들이는 것이 중요합니다.
> 

## 🖥️ EC2 만들 때 태그 넣는 방법

1. EC2 콘솔에서 **[인스턴스 시작]** 클릭
2. 이름 · AMI · 인스턴스 유형 등 평소대로 설정
3. 화면 아래로 스크롤 → **[태그]** 섹션 찾기 (또는 "태그 추가" 링크)
4. **[태그 추가]** 클릭 후 입력
    - 키(Key): `Team`
    - 값(Value): `team3`
5. 나머지 설정을 마치고 **[인스턴스 시작]**

> 콘솔 UI가 업데이트되면 메뉴 위치가 조금 다를 수 있습니다. "태그" 또는 "Tags" 글자를 찾으면 됩니다.
> 

## 🤝 팀원과 리소스 공유하기

- 같은 계정 안에 있으면 **팀원의 리소스가 자동으로 보입니다.** 별도 공유 설정이 필요 없습니다.
- 팀 공용 VPC · EC2 · 클러스터 · S3 등을 함께 사용하면 됩니다.
- 단, **팀 태그가 붙어 있어야** 서로 원활하게 관리할 수 있습니다. (위 태그 규칙 참고)

# 기술 가이드

# 📜 공통 원칙

- AWS 리소스는 반드시 **서울 리전(`ap-northeast-2`)**에서 생성합니다.
- 생성한 리소스의 이름, 역할, 리전, 가용 영역, 담당자를 구성 명세에 기록합니다.
- 모든 리소스에는 팀과 프로젝트를 구분할 수 있는 태그를 설정합니다.

```
Project=lion
Team=Team3
Owner=이정제
```

- Access Key, Secret Access Key, DB 비밀번호, 인증서 및 토큰은 GitHub, Notion, 발표 자료, 화면 캡처에 노출하지 않습니다.
- 보안 그룹은 필요한 포트와 출발지만 허용하고, `0.0.0.0/0` 전체 허용은 최소화합니다.
- 데이터베이스는 가능하면 외부에 공개하지 않고, EC2 서버를 통해서만 접근하도록 구성합니다.
- 비용이 많이 발생할 수 있는 리소스는 생성 전 팀원과 확인합니다.
- 프로젝트 종료 후 불필요한 EC2, RDS, NAT Gateway, Load Balancer, Elastic IP, EBS 등을 반드시 삭제하거나 중지합니다.
- 처음부터 모든 확장 구성을 적용하기보다 다음 순서로 진행합니다.

```
기본 아키텍처 설계
→ 네트워크 구축
→ 서버 구축
→ 스토리지 구축
→ 데이터베이스 연동
→ 정상 동작 확인
→ 확장 및 모니터링 구성
```

# 🎯 2. 프로젝트 목표 및 산출물

## 2.1 프로젝트 목표

1. 서비스 요구사항을 바탕으로 AWS 아키텍처를 설계합니다.
2. VPC, Subnet, Route Table, Internet Gateway를 활용하여 가상 네트워크 공간을 구성합니다.
3. EC2 서버와 EBS·S3 스토리지를 생성합니다.
4. EC2 서버에서 Docker 컨테이너 또는 웹 애플리케이션을 실행합니다.
5. Amazon RDS를 활용하여 애플리케이션과 연결되는 데이터베이스 서버를 구축합니다.
6. 보안 그룹과 네트워크 경로를 설정하여 사용자, 서버, 데이터베이스 간 통신을 정상화합니다.
7. 기본 환경 구축 후 ALB, Auto Scaling, Multi-AZ 등 확장 가능한 구조를 적용합니다.
8. CloudWatch를 활용하여 주요 리소스의 상태와 지표를 확인합니다.

## 2.2 필수 산출물

- AWS 아키텍처 구성도
- 서비스 요구사항 정의서
- AWS 리소스 구성 명세서
- VPC 및 Subnet 설계표
- Route Table 및 Internet Gateway 구성
- 보안 그룹 인바운드·아웃바운드 규칙
- EC2 서버 생성 및 접속 증빙
- Docker 컨테이너 실행 증빙
- EBS 또는 S3 사용 증빙
- RDS 생성 및 EC2 연동 증빙
- 데이터 입력 및 조회 결과
- 서비스 외부 접속 화면
- 트러블슈팅 기록
- 프로젝트 회고
- 비용 발생 리소스 정리 결과

## 2.3 선택 산출물

- Application Load Balancer 구성
- Auto Scaling Group 구성
- RDS Multi-AZ 구성
- RDS Storage Auto Scaling 적용
- CloudWatch Alarm 구성
- IAM Role을 활용한 EC2와 S3 연결
- HTTPS 또는 도메인 연결
- 인프라 구축 자동화 자료

# 🧩 4. AWS 아키텍처 설계

## 4.1 권장 설계 순서

1. 프로젝트에서 제공할 서비스를 정의합니다.
2. 사용자가 어떤 경로를 통해 서비스에 접속하는지 정의합니다.
3. 외부에 공개할 리소스와 내부에서만 사용할 리소스를 구분합니다.
4. 서버, 스토리지, 데이터베이스의 역할을 정합니다.
5. 각 리소스가 위치할 VPC, 가용 영역, Subnet을 정합니다.
6. 필요한 통신 포트와 보안 그룹을 설계합니다.
7. 데이터 저장과 조회 흐름을 설계합니다.
8. 장애 또는 트래픽 증가 시 확장 방법을 정합니다.
9. 서비스별 예상 비용과 구현 가능성을 확인합니다.

## 4.2 권장 네트워크 설계

| 항목 | 권장 값 | 비고 |
| --- | --- | --- |
| AWS Region | `ap-northeast-2` | 서울 리전 |
| VPC CIDR | `10.14.0.0/16` | 팀별로 조정 가능 |
| Public Subnet A | `10.14.1.0/24` | `ap-northeast-2a` |
| Public Subnet C | `10.14.2.0/24` | `ap-northeast-2c` |
| Private Subnet A | `10.14.11.0/24` | RDS 배치용 |
| Private Subnet C | `10.14.12.0/24` | RDS 및 확장 구성용 |
| Internet Gateway | 1개 | VPC에 연결 |
| Public Route | `0.0.0.0/0 → IGW` | 외부 인터넷 통신 |
| DB Subnet Group | Private Subnet 2개 | RDS 생성 시 사용 |

> 최소 구성에서는 Public Subnet 1개와 EC2 1대로 시작할 수 있습니다.
> 
> 
> RDS는 가능하면 Public Access를 비활성화하고 Private Subnet에 배치합니다.
> 

## 4.3 아키텍처 구성도 필수 표기 항목

- AWS Region
- Availability Zone
- VPC CIDR
- Public Subnet과 Private Subnet 구분
- Subnet별 CIDR
- EC2의 위치와 역할
- S3의 용도
- RDS의 위치와 역할
- Internet Gateway 연결
- Route Table 연결
- 보안 그룹 간 통신 방향
- 사용자 접속 흐름
- 데이터 저장 및 조회 흐름
- ALB 및 Auto Scaling 적용 여부
- RDS Multi-AZ 적용 여부

## 4.4 아키텍처 검토 질문

- 사용자가 서비스에 정상적으로 접속할 수 있는가?
- EC2가 외부 인터넷과 통신할 수 있는가?
- RDS가 외부에 직접 노출되어 있지 않은가?
- EC2에서만 RDS에 접근할 수 있는가?
- 파일과 데이터가 각각 어디에 저장되는가?
- 서버 장애 시 서비스가 모두 중단되는 구조인가?
- 트래픽 증가 시 서버를 확장할 수 있는가?
- 불필요하게 비용이 발생하는 리소스가 포함되어 있지 않은가?

# 🏷️ 5. 리소스 네이밍 및 태그 규칙

> ⚠️ **이 절이 이 프로젝트의 실제 구속력 있는 규칙입니다** (2026-08-20 기준, `terraform/` 코드에 실제 적용·검증 완료). 원래 이 문서는 부트캠프 공용 템플릿이라 절마다 예시 값이 달랐지만(5절은 `lion-team3-*`, 18절은 `p2-team1-*`), 아래 표는 그 템플릿의 **패턴**만 가져와 이 프로젝트(책 먹는 사자, EKS/Aurora 기반)의 실제 리소스에 맞게 확정한 값입니다. 설계/아키텍처 판단은 `docs/개발 문서`가 우선하며, 이 절은 오직 **이름·태그 규칙**만을 다룹니다.

## 5.1 기본 패턴

```
lion-team3-{environment}-{역할}[-{부가식별자}]
```

- `{environment}` = `dev` 또는 `prod`
- `{역할}`은 리소스가 하는 일을 그대로 씀 (예: `karpenter-node`, `aurora-sg`) — 템플릿의 `-번호` 대신 **역할명 + 필요시 가용영역/순번**을 사용 (예: `web-01`처럼 단순 번호를 붙이는 대신, 이 프로젝트는 `public-ap-northeast-2a`처럼 가용영역을 붙이는 식이 더 명확해서 그렇게 함)

# 🌐 6. VPC 및 가상 네트워크 구성

## 6.1 VPC 생성

1. VPC 콘솔에서 새 VPC를 생성합니다.
2. IPv4 CIDR을 입력합니다.

```
10.14.0.0/16
```

1. DNS Resolution과 DNS Hostnames 설정을 확인합니다.
2. Name 태그와 프로젝트 태그를 설정합니다.
3. 생성한 VPC 정보를 구성 명세에 기록합니다.

## 6.2 Subnet 생성

- 외부 접속이 필요한 EC2와 ALB는 Public Subnet에 배치합니다.
- 데이터베이스는 Private Subnet에 배치합니다.
- 확장 구성을 위해 서로 다른 가용 영역에 Subnet을 생성합니다.

| Subnet | 가용 영역 | CIDR | 역할 |
| --- | --- | --- | --- |
| Public A | `ap-northeast-2a` | `10.14.1.0/24` | EC2 및 ALB |
| Public C | `ap-northeast-2c` | `10.14.2.0/24` | EC2 및 ALB |
| Private A | `ap-northeast-2a` | `10.14.11.0/24` | RDS |
| Private C | `ap-northeast-2c` | `10.14.12.0/24` | RDS |

## 6.3 Internet Gateway 구성

1. Internet Gateway를 생성합니다.
2. 생성한 Internet Gateway를 프로젝트 VPC에 연결합니다.
3. Public Route Table에 Internet Gateway 경로를 추가합니다.

```
Destination: 0.0.0.0/0
Target: Internet Gateway
```

## 6.4 Route Table 구성

### Public Route Table

```
VPC 내부 통신: Local
외부 인터넷 통신: 0.0.0.0/0 → Internet Gateway
```

Public Subnet을 Public Route Table에 연결합니다.

### Private Route Table

```
VPC 내부 통신: Local
```

Private Subnet을 Private Route Table에 연결합니다.

> Private Subnet에서 외부 인터넷 통신이 반드시 필요한 경우 NAT Gateway를 사용할 수 있습니다.
> 
> 
> NAT Gateway는 지속적으로 비용이 발생할 수 있으므로 필요성을 검토한 후 생성합니다.
> 

## 6.5 네트워크 확인 항목

- [ ]  VPC CIDR과 Subnet CIDR이 겹치지 않음
- [ ]  Public Subnet과 Private Subnet이 구분됨
- [ ]  Public Subnet이 Public Route Table과 연결됨
- [ ]  Public Route Table에 Internet Gateway 경로가 존재함
- [ ]  EC2에 Public IPv4 주소가 할당됨
- [ ]  RDS는 Private Subnet에 위치함
- [ ]  필요한 보안 그룹 포트가 허용됨
- [ ]  RDS는 EC2 보안 그룹의 접근만 허용함

# 🔐 7. 보안 그룹 설계

## 7.1 Web Server Security Group

| 유형 | 포트 | 출발지 | 비고 |
| --- | --- | --- | --- |
| SSH | 22 | 본인 공인 IP | SSH 사용 시 |
| HTTP | 80 | `0.0.0.0/0` | 웹 서비스 공개 |
| HTTPS | 443 | `0.0.0.0/0` | HTTPS 적용 시 |
| Custom TCP | 3000 | 필요한 출발지 | 애플리케이션 포트 예시 |
| Custom TCP | 8080 | 필요한 출발지 | 애플리케이션 포트 예시 |

## 7.2 Database Security Group

| DB 엔진 | 포트 | 출발지 |
| --- | --- | --- |
| MySQL | 3306 | Web Server Security Group |
| PostgreSQL | 5432 | Web Server Security Group |

> RDS 보안 그룹의 출발지를 `0.0.0.0/0`로 설정하지 않습니다.
> 
> 
> EC2에 연결된 Web Server Security Group을 출발지로 지정합니다.
> 

## 7.3 ALB Security Group

| 유형 | 포트 | 출발지 |
| --- | --- | --- |
| HTTP | 80 | `0.0.0.0/0` |
| HTTPS | 443 | `0.0.0.0/0` |

ALB를 사용하는 경우 EC2 보안 그룹의 HTTP 출발지는 전체 인터넷이 아니라 ALB Security Group으로 제한할 수 있습니다.

```
사용자
→ ALB Security Group
→ EC2 Security Group
→ RDS Security Group
```

## 7.4 보안 그룹 점검

- [ ]  SSH 포트가 전체 인터넷에 개방되어 있지 않음
- [ ]  웹 서비스에 필요한 포트만 개방함
- [ ]  RDS 포트가 전체 인터넷에 개방되어 있지 않음
- [ ]  EC2에서 RDS로 필요한 포트만 접근 가능함
- [ ]  사용하지 않는 인바운드 규칙을 제거함
- [ ]  보안 그룹의 이름과 역할이 명확함

## 9.2 Amazon S3

S3는 다음과 같은 파일을 저장할 때 활용할 수 있습니다.

- 이미지
- 정적 파일
- 결과물
- 로그
- 백업 파일
- 사용자 업로드 파일

### 권장 설정

- Bucket Public Access Block 유지
- 서버 측 암호화 설정
- Bucket Versioning 선택 적용
- EC2 접근 시 IAM Role 사용

### AWS CLI 확인

```
aws sts get-caller-identity
aws s3 ls
```

### 파일 업로드

```

```

### 업로드 결과 확인

```
aws s3 ls s3://<BUCKET_NAME>/
```

> 웹 사이트 공개가 필요하더라도 Bucket 전체 공개보다는 제한된 정책 또는 CloudFront 사용을 우선 검토합니다.
>

4. EC2에서 AWS CLI를 통해 접근을 확인합니다.

```
aws sts get-caller-identity

```

> Access Key와 Secret Access Key를 코드 또는 서버에 직접 저장하지 않습니다.

## 12.1 Application Load Balancer

1. 서로 다른 가용 영역에 Public Subnet을 준비합니다.
2. EC2 2대 또는 Auto Scaling Group을 준비합니다.
3. Target Group을 생성합니다.
4. EC2 인스턴스를 Target Group에 등록합니다.
5. Health Check 경로를 설정합니다.
6. ALB Listener의 HTTP 80 포트를 Target Group으로 전달합니다.
7. Target Health가 `healthy`인지 확인합니다.
8. ALB DNS 이름으로 서비스에 접속합니다.

## 12.2 Target Group 확인

- Target Type이 올바른지
- Target Port가 애플리케이션 포트와 일치하는지
- Health Check Path가 실제 응답 경로와 일치하는지
- EC2 Security Group이 ALB Security Group의 접근을 허용하는지
- Target 상태가 `healthy`인지

## 12.3 Auto Scaling Group

### 권장 구성

| 항목 | 권장 값 |
| --- | --- |
| 최소 용량 | 1 |
| 희망 용량 | 2 |
| 최대 용량 | 3 |
| Subnet | 서로 다른 가용 영역의 Subnet |
| Target Group | ALB Target Group 연결 |
| Scaling Policy | CPU 또는 요청 수 기준 |

### 구성 순서

1. Launch Template을 생성합니다.
2. AMI, Instance Type, Security Group을 설정합니다.
3. User Data를 이용하여 애플리케이션 실행을 자동화합니다.
4. Auto Scaling Group을 생성합니다.
5. 최소, 희망, 최대 용량을 설정합니다.
6. ALB Target Group에 연결합니다.
7. Scaling Policy를 설정합니다.
8. 인스턴스 생성 및 Target 등록 결과를 확인합니다.

> 설정 화면만 캡처하는 것보다 인스턴스 수 변화 또는 Target 등록 결과를 증빙합니다.

# 🧯 15. 막혔을 때 확인 순서

## 15.1 EC2에 접속할 수 없음

확인할 사항:

- EC2 상태가 `running`인지
- Public IPv4 주소가 있는지
- Public Subnet에 위치하는지
- Route Table에 Internet Gateway 경로가 있는지
- Security Group에서 22 포트를 본인 IP에 허용했는지
- Key Pair 또는 Instance Connect 설정이 올바른지
- Network ACL에서 통신을 차단하고 있지 않은지

```
ssh -i <KEY_FILE> <USER>@<EC2_PUBLIC_IP>
```

## 15.2 웹 페이지에 접속할 수 없음

```
systemctl status nginx
sudo ss -lntp
curl http://localhost

sudo docker ps
sudo docker logs <CONTAINER_NAME>
```

확인할 사항:

- Nginx 또는 컨테이너가 실행 중인지
- 애플리케이션이 `0.0.0.0`에 Listen 중인지
- Security Group에서 서비스 포트를 허용했는지
- Docker Port Mapping이 올바른지
- EC2 Public IPv4 주소가 올바른지
- ALB Target이 Healthy 상태인지

## 15.3 EC2에서 RDS에 접속할 수 없음

```
nslookup <RDS_ENDPOINT>

nc -zv <RDS_ENDPOINT> 3306
nc -zv <RDS_ENDPOINT> 5432
```

확인할 사항:

- RDS 상태가 `available`인지
- EC2와 RDS가 동일한 VPC에 있는지
- RDS Endpoint가 올바른지
- DB Security Group이 EC2 Security Group을 허용하는지
- 포트가 DB Engine과 일치하는지
- Username과 Database Name이 올바른지
- DB Subnet Group이 정상적으로 구성되어 있는지
- Network ACL이 통신을 차단하지 않는지

## 15.4 S3 업로드가 거부됨

```
aws sts get-caller-identity
aws s3 ls s3://<BUCKET_NAME>/
```

확인할 사항:

- EC2 IAM Role이 연결되어 있는지
- IAM Policy에 필요한 권한이 있는지
- Bucket Policy에서 접근을 차단하고 있지 않은지
- Bucket 이름과 Object 경로가 정확한지
- 다른 리전의 Bucket을 사용하고 있지 않은지

## 15.5 ALB Target이 Unhealthy 상태임

확인할 사항:

- Health Check Path가 실제 응답 경로와 일치하는지
- Target Port와 애플리케이션 포트가 일치하는지
- EC2 Security Group이 ALB Security Group의 접근을 허용하는지
- 애플리케이션이 정상적으로 실행 중인지
- Health Check 요청에 정상 HTTP 상태 코드를 반환하는지
- Target이 올바른 가용 영역과 Subnet에 위치하는지

## 15.6 Docker 컨테이너가 종료됨

```
sudo docker ps -a
sudo docker logs <CONTAINER_NAME>
sudo docker inspect <CONTAINER_NAME>
```

확인할 사항:

- 애플리케이션 실행 명령어가 올바른지
- 환경변수가 정상적으로 전달되었는지
- 컨테이너 내부 포트가 올바른지
- RDS 연결 정보가 정확한지
- 이미지 빌드가 정상적으로 완료되었는지

## 15.7 비용이 예상보다 많이 발생함

우선 확인할 리소스:

- NAT Gateway
- 실행 중인 EC2
- RDS
- Application Load Balancer
- 사용하지 않는 Elastic IP
- EBS Volume
- EBS Snapshot
- 데이터 전송량

> 비용이 발생하는 리소스는 프로젝트 종료 직후 팀별 정리 담당자가 확인합니다.

# 🚀 20. 배포 방법 (Terraform 배포 런북)

> ⚠️ 이 절도 §5와 마찬가지로 **이 프로젝트의 실제 구속력 있는 절차**입니다 (2026-08-20 작성). §8/§10의 EC2·RDS 콘솔 가이드는 부트캠프 템플릿이 가정한 단일 EC2+RDS 구조용이라 이 프로젝트(계층형 Terraform + EKS)엔 적용되지 않으니 무시하고 이 절만 따르세요. 더 자세한 근거(모듈별 왜 이 순서인지)는 `docs/개발 문서/TERRAFORM_STRUCTURE.md` §5를 참고합니다.

## 20.1 사전 준비 (Prerequisites)

- [ ] `aws sts get-caller-identity`로 자격 증명 확인 (리전: `ap-northeast-2`)
- [ ] Terraform `>= 1.8.0` 설치 확인
- [ ] **State 백엔드가 미리 존재해야 함** — `book-eating-lion-tfstate-{env}` S3 버킷과 `book-eating-lion-tflock-{env}` DynamoDB 테이블(dev/prod 각각). 이 저장소엔 이 둘을 만드는 부트스트랩 코드가 없으므로 **최초 1회는 수동으로(또는 별도 부트스트랩 스크립트로) 먼저 만들어야** `terraform init`이 됩니다.
- [ ] `terraform.tfvars`의 TODO 표시된 placeholder 값(도메인, S3 버킷명, 알림 이메일 등, §5.3 예외 표 참고) 실제 값으로 교체 확인

## 20.2 환경 간 순서 — **prod/00-base를 dev/00-base보다 먼저** apply

GitHub OIDC Provider(`aws_iam_openid_connect_provider`)는 AWS 계정당 URL 하나에 유일한 전역 리소스입니다. 이 프로젝트는 `prod/00-base`가 실제로 생성(`create_oidc_provider = true`)하고, `dev/00-base`는 데이터소스로 조회만 합니다(`create_oidc_provider = false`). 그래서 **`prod/00-base`가 최소 한 번 apply되기 전엔 `dev/00-base`를 apply할 수 없습니다.** 이건 계층 순서(20.3)와 별개로 이 프로젝트에만 있는 환경 간 의존성입니다.

## 20.3 계층 순서 (환경 하나 기준: `dev` 또는 `prod`)

```
00-base → 01-data → 02-runtime
```

각 계층은 상위 계층의 출력을 SSM Parameter Store로 조회하므로(§4 계층 간 데이터 연동 표준), 반드시 이 순서로 apply해야 합니다. `{env}`를 `dev` 또는 `prod`로 바꿔서 그대로 실행합니다.

```bash
# 1. Base 계층 (VPC, 서브넷, ECR, S3, Route53, ACM, WAF, SNS, GitHub OIDC)
cd terraform/environments/{env}/00-base
terraform init
terraform plan -out=tfplan
terraform apply tfplan

# 2. Data 계층 (dev: EC2 PostgreSQL / prod: Aurora, RDS Proxy, Valkey, Cognito)
cd ../01-data
terraform init
terraform plan -out=tfplan
terraform apply tfplan

# 3. Runtime 계층 (EKS → Karpenter → ALB Controller → CloudFront/AI IRSA)
cd ../02-runtime
terraform init
# 3-1. 클러스터부터 먼저 생성 — Karpenter/ALB Controller의 kubernetes/helm provider가
#      인증할 EKS 클러스터가 아직 없으면 이 단계에서 provider 초기화 자체가 실패한다.
terraform apply -target=module.eks_cluster
# 3-2. 나머지(Karpenter, ALB Controller, edge_routing, AI 서비스 IAM) 적용
terraform plan -out=tfplan
terraform apply tfplan
```

> **왜 `plan -out` 후 사람이 확인하고 `apply tfplan`을 쓰는가:** `00-base`/`01-data`는 위험 등급 **Critical**입니다(계층별 위험도 매트릭스는 `docs/개발 문서/TERRAFORM_STRUCTURE.md` §1 참고). `-auto-approve`는 쓰지 않고, diff를 사람이 읽은 뒤 승인하는 2단계를 항상 거칩니다. `02-runtime`도 신규 인프라를 처음 세울 때는 동일 절차를 따르되, 이후 반복 배포(서비스 라우트 추가 등)부터는 팀 판단에 따라 CI로 자동화해도 됩니다.

## 20.4 자원 정리 및 삭제 순서 (배포 역순)

```bash
cd terraform/environments/{env}/02-runtime && terraform plan -destroy -out=destroy.tfplan && terraform apply destroy.tfplan
cd ../01-data                                && terraform plan -destroy -out=destroy.tfplan && terraform apply destroy.tfplan
cd ../00-base                                && terraform plan -destroy -out=destroy.tfplan && terraform apply destroy.tfplan
```

> `01-data`는 Aurora/Valkey 등 영속 데이터를 담은 Critical 계층이라 삭제 전 반드시 `plan -destroy`로 무엇이 지워지는지 사람이 먼저 확인합니다. dev처럼 데이터 유실이 문제되지 않는 환경에서만 팀 판단으로 `-auto-approve`를 써도 됩니다. `prod/00-base`를 삭제하려면 그 전에 `dev/00-base`부터 먼저 삭제해야 합니다(20.2의 OIDC Provider 소유 관계가 반대로도 적용됨).
