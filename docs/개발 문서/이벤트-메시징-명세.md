## 2. EPUB 등록 → ai

용도: 파싱 → 페이지 분할 → 임베딩 → S3 Vectors 적재 → `wiki_books` 등록

### 메시지

```json
{ "bookId": 42, "title": "운수 좋은 날", "category": "한국근대소설", "epubS3Key": "books/42/unsu.epub" }
```

| 필드 | 필수 | 비고 |
| -- | -- | -- |
| `bookId` | O | 벡터 키의 앞부분 |
| `title` | O | 인제스트 시점 스냅샷. 인용에 이 값이 나간다 |
| `category` | X | 벡터 메타데이터 |
| `epubS3Key` | O | 없으면 발행하지 않는다 |

### 발행측 — 미구현  [7]

| 단계 | 작업 |
| -- | -- |
| 1 | `ALTER TABLE catalog_db.books ADD COLUMN epub_s3_key VARCHAR(500);` [8] |
| 2 | `Book` 필드 · `AdminBookCreateRequest` (`@Size(max=500)`) · `AdminBookService` 빌더 |
| 3 | `AdminBookService.create()` — 저장 후 · `epubS3Key` 있을 때만 · 커밋 이후 발행 |

### 소비측 — 완료

| 파일 | 역할 |
| -- | -- |
| `apps/ai-api/.../ingest/SqsIngestListener` | `app.ai.sqs.enabled=true` 일 때만. **1건씩** [9] |
| `modules/ai/.../ingest/BookIngestService` | 파이프라인 본체 |
| `modules/ai/.../ingest/WikiBookRegistrar` | 등록 트랜잭션 분리 [10] |
| `modules/ai/.../epub/EpubTextExtractor` | spine 순서 파싱, 목차·라이선스 제거 |
| `modules/ai/.../epub/TextSplitter` | 900자 = 1페이지, 페이지 내 청크 분할 |
| `apps/ai-api/.../client/S3ObjectStorageAdapter` | EPUB 원본 다운로드 |
| `apps/ai-api/.../client/S3VectorIndexAdapter` | 벡터 put · delete · count |

### 불변식

| 항목 | 내용 |
| -- | -- |
| 등록 순서 | 벡터 적재 + 건수 검증 이후에만 `wiki_books` 등록 [11] |
| 멱등 | 벡터 키 `{bookId}#{page}#{chunkSeq}` 결정적 + delete-then-put |
| 과금 방어 | `wiki_books.source_hash` (SHA-256) 동일 시 임베딩 스킵 |
| 부분 실패 검출 | 적재 후 GetVectors 건수 대조, 불일치 시 예외 |
| ID 충돌 가드 | 같은 `bookId` 에 다른 제목이면 예외 [12] |

## 4. 추천 벡터 갱신 → ai

용도: 추천 인덱스(`recommendation-books-v1`)를 최신 상태로 유지. RAG/EPUB 질의용 `wiki-v1` 인덱스와는 완전히 별개입니다(`db-erd-v2.md`의 ai_db 섹션 참고).

채널: Redis Streams. catalog-api가 도서 등록/수정/삭제 시 발행하고, ai-api(`RecommendationBookStreamConfig`)가 소비해서 인덱스를 갱신합니다.

발행측/소비측 모두 구현 완료로 확인되었습니다. 세부 메시지 필드·컨슈머 그룹명 등은 이후 필요할 때 채워넣습니다.

## 5. 인프라 — 전부 미구축

> ⚠️ 아래는 SQS 관련 IaC(Terraform)가 없다는 뜻입니다. `book-purchase-queue`의 발행/소비 애플리케이션 코드는 실제로 동작하는 것으로 확인됐으므로(§1), 최소한 그 큐는 로컬(localstack 등) 또는 별도 환경에 이미 어떤 형태로든 존재할 가능성이 있습니다 — "테라폼으로 관리되는 정식 인프라가 없다"는 의미로 읽어주세요.

### 5-1. 큐

| 큐 | 발행 | 소비 | Visibility Timeout |
| -- | -- | -- | -- |
| `book-ingest-queue` | catalog-api | ai-rag | **300초** [16] |
| `book-purchase-queue` | order-api | ai-rag | 30초 |

각 큐에 DLQ (`*-dlq`, `maxReceiveCount: 3`). 표준 큐로 충분 [17]

### 5-2. IAM

| 주체 | 권한 |
| -- | -- |
| catalog-api pod | `sqs:SendMessage` (ingest) |

### 5-3. ConfigMap

`k8s/{ai,catalog,order}/configmap.yaml` 에 `SQS` 키 0건. 기본값이 `false` 라 배포해도 두 리스너 다 꺼진 채 뜬다.

## 참고

[1] (해결됨) 이 문서 검증 시점(`6af8640`)엔 `publish()` 호출자가 0건이었으나, 이후 `OrderService.java:238`에서 호출이 추가되어 지금은 정상 발행됩니다.

[2] 유실되면 산 책을 못 읽는데, 에러가 아니라 "근거를 못 찾았습니다" 로만 보인다. 그래서 휘발 채널을 쓰지 않는다.

[3] 숫자 `member_id` 를 보내면 행은 정상 저장되고 에러도 나지 않는다. 다만 질의 시 교집합이 비어 `grounded=false` 만 돌아온다. 이 계약에서 가장 조용히 깨지는 지점. order 가 `sub` 를 모르면 결제 요청 JWT 의 `sub` 클레임에서 꺼낸다.

[4] 트랜잭션 안에서 보내면 결제가 롤백돼도 메시지는 이미 나가 있어, 사지 않은 책을 읽을 수 있게 된다.

[5] `modules/book` 이 AWS SDK 를 직접 의존하지 않는 것과 같은 이유.

[6] 핸들러가 정상 반환했을 때만 메시지를 삭제한다. 실패 시 미삭제 → 재배달 → DLQ. 폴링 예외로 루프를 끝내지 않는다 — 여기서 죽으면 파드는 살아 있는데 소비만 멈추고 헬스체크도 통과해 가장 늦게 발견된다.

[7] `modules/book` 전체에 `epub` 문자열 0건. 컬럼·엔티티 필드·DTO·발행 코드 전부 없다.

[8] `catalog-api/application-local.yml` 의 Flyway 가 `enabled: false` 이고 마이그레이션 파일 0개다. 그냥 켜면 *Found non-empty schema without schema history table* 로 기동이 깨진다. 켤 거면 `baseline-on-migrate: true` 동반.

[9] 임베딩이 외부 API 라 여러 권을 동시에 돌리면 Bedrock 스로틀링에 걸리고, 재시도가 겹치면 비용만 늘어난다. `epubS3Key` 가 없는 메시지는 정상 반환해 삭제한다 — 실패가 아니라 "인제스트 대상 아님".

[10] 같은 클래스에서 부르면 자기 호출이라 `@Transactional` 이 조용히 무효가 된다.

[11] `wiki_books` 행이 곧 "검색 가능한 책" 이다. 반대로 하면 벡터가 반만 들어간 책이 목록에 뜬다.

[12] 조용히 덮어쓰면 기존 벡터가 지워지고, 그 책을 먹은 사용자가 먹은 적 없는 책을 먹은 상태가 된다. 테스트 책의 벡터 ID는 `900001~900005` 를 쓴다. `catalog_db.books` 는 IDENTITY 라 겹치지 않지만 ID 를 수동 배정하지 말 것.

[13] 동기 호출로 바꾸면 리뷰 작성이 결제 서비스 가용성에 종속돼, "장애가 결제로 전이되지 않는다" 는 명분과 정반대가 된다. Phase 1.5 통합 게이트 기준은 "주문 확정 → 리뷰 작성 가능까지 5초 이내".

[14] 구매 확정 시점 스냅샷이라 원본이 바뀌어도 갱신하지 않는다. 사용자가 닉네임을 바꿔도 과거 리뷰는 당시 이름으로 남는다.

[15] `modules` 끼리는 의존할 수 없어 발행측(order)·소비측(catalog)이 공유할 스키마를 `common` 에 둔다. 도메인 코드가 아니라 계약이다.

[16] 청크 1개당 임베딩 1회, 장편은 200~500청크. 처리 시간이 VT 를 넘으면 처리 중인 책이 재배달되어 중복 임베딩 = 중복 과금.

[17] 벡터 키가 결정적이고 처리가 멱등이라 순서가 결과를 바꾸지 않는다. DLQ 는 파싱 불가 메시지가 큐를 영원히 돌지 않게 하는 유일한 장치.

[18] 빠지기 쉽다. ai 는 현재 S3 Vectors 만 접근하고 일반 S3 는 쓰지 않는다.
