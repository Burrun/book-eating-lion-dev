# 인프라 배포 트러블슈팅 이력

실제 배포(dev/prod) 중 겪은 문제와 원인·해결을 시간 순으로 기록합니다. `terraform/인프라구성명세.md` §7이 "어떻게 배포하는가"라면, 이 문서는 "배포하다 뭐가 터졌고 왜였는가"입니다 — 새 배포 오류를 겪으면 원인을 못 찾고 헤매기 전에 먼저 이 문서를 훑어보세요. 같은 원인이 다른 서비스에서 반복되는 경우가 많습니다.

새 항목을 추가할 땐 번호를 이어서, 아래 형식을 따릅니다:

```
**N (상태, 관련 PR/커밋) 한 줄 증상**

원인 → 어디를 고쳤는지 → 남은 일(있다면). 날짜.
```

상태는 `해결` / `미해결` / `진행 중` 중 하나로 표기합니다.

## 2026-08-20 — CI/CD 첫 실행

`workflow_dispatch`로 `main-cd.yml`을 처음 돌렸을 때 겪은 문제들. 전부 해결.

**① `Not authorized to perform sts:AssumeRoleWithWebIdentity`**

GitHub이 OIDC 토큰의 `sub` claim 기본 형식을 리포지킹(repojacking) 방지 목적으로 바꿨습니다.

```
예전: repo:OWNER/REPO:ref:refs/heads/BRANCH
현재: repo:OWNER@ownerId/REPO@repoId:ref:refs/heads/BRANCH   (예: repo:Burrun@127071470/book-eating-lion-dev@1318056441:ref:refs/heads/dev)
```

`github_oidc` 모듈의 trust policy가 옛날 형식(`repo:OWNER/REPO:*`)만 매치하도록 돼 있어서 전부 `AccessDenied`. CloudTrail의 `AssumeRoleWithWebIdentity` 이벤트(`userIdentity.principalId`)로 실제 `sub` 값을 확인하고 원인을 특정했습니다. `repo:${github_org}@*/${github_repo}@*:*`처럼 ID 부분을 와일드카드로 열어서 해결(`terraform/modules/base/github_oidc/main.tf`).

**② OIDC는 통과했는데 S3/EKS 권한이 부족함**

- `Sync to Amazon S3`: `s3:ListBucket` `AccessDenied` — CI 역할(`github_actions`)에 S3 권한 자체가 없었음. `frontend_bucket_arn`/`media_bucket_arn`을 `github_oidc` 모듈에 넘겨 `s3:ListBucket`(버킷)/`GetObject`·`PutObject`·`DeleteObject`(객체)와 `cloudfront:CreateInvalidation`을 추가.
- `kubectl apply` (`01-namespace.yaml`): `namespaces is forbidden` — CI 역할의 EKS access policy가 `AmazonEKSAdminPolicy`(K8s 내장 `admin` ClusterRole)였는데, 이건 네임스페이스 **안**의 리소스만 관리하고 Namespace 객체 자체 같은 cluster-scoped 리소스는 못 만듭니다. `admin_principal_arns`(사람)와 같은 `AmazonEKSClusterAdminPolicy`(`cluster-admin` 매핑)로 교체(`terraform/modules/compute/eks_cluster/main.tf`).

두 경우 다 `00-base`(①②의 S3 부분) / `02-runtime`(②의 EKS 부분) 재apply로 반영됩니다 — 리소스 재생성 없이 IAM policy/access entry만 update-in-place.

**③ ECR 리포지토리 이름에 레지스트리 주소가 두 번 붙음**

`k8s/*/deployment*.yaml`과 `main-cd.yml`의 `Build & push image` 스텝은 둘 다 `${ECR_REGISTRY}/${ECR_*_REPO}` 형태로 직접 조합합니다 — 즉 `ECR_CATALOG_REPO` 같은 Variable엔 **레지스트리 주소 없는 순수 리포 이름**(`lion-team3-dev/catalog`)만 들어가야 합니다. `sync-github-config.sh`가 처음엔 레지스트리 주소까지 합친 전체 URI를 넣도록 돼 있어서, 조합 시 레지스트리가 두 번 붙은 잘못된 이미지 이름(`...amazonaws.com/...amazonaws.com/lion-team3-dev/catalog`)이 됐고, 그 이름의 리포지토리는 당연히 존재하지 않아 `ecr:InitiateLayerUpload`가 (권한이 아니라 대상 자체가 없어서) `denied`로 실패했습니다. 스크립트를 순수 리포 이름만 넣도록 고쳤습니다 — 이미 등록된 값이 있다면 `./scripts/sync-github-config.sh {env}` 재실행으로 정정됩니다.

**④ 파드가 `exec format error`로 CrashLoopBackOff**

`order`/`member` 서비스가 ECR push까지는 성공하고 `kubectl apply`도 성공하는데, 파드가 계속 죽습니다:

```
exec /opt/java/openjdk/bin/java: exec format error
```

**원인**: CPU 아키텍처 불일치. Karpenter `NodePool`이 `kubernetes.io/arch: arm64`만 요구하도록 돼 있어(비용 절감 목적) 클러스터 노드가 전부 Graviton(arm64)인데, `main-cd.yml`의 `docker build`는 GitHub `ubuntu-latest` 러너(amd64)에서 `--platform` 지정 없이 빌드해서 이미지가 amd64로 나옵니다. amd64 바이너리를 arm64 커널에 올리니 즉시 죽는 것.

검토한 옵션 3가지 — A) CI를 arm64로 buildx 크로스빌드, B) NodePool을 amd64로 되돌림, C) GitHub arm64 호스팅 러너 사용. **B(NodePool을 amd64로 되돌림)**를 적용 — `modules/compute/karpenter/main.tf`의 NodePool 요구사항이 `kubernetes.io/arch: amd64`로 고정돼 있습니다. Graviton으로 다시 전환하려면 A 또는 C를 먼저 적용한 뒤 되돌릴 것.

## 2026-08-21 — Karpenter 노드/네트워크/SQS 배선

**⑤ Karpenter가 EC2는 띄우는데 노드로 영영 등록 안 됨 (`Launched=True`, `Registered=Unknown`에서 멈춤)**

클러스터가 `authenticationMode = "API"`(aws-auth ConfigMap 없이 EKS Access Entry만 사용)인데, Karpenter가 만드는 노드의 IAM Role(`lion-team3-{env}-karpenter-node`)에 Access Entry가 없었습니다. EKS Managed NodeGroup(시스템 노드그룹)은 EKS가 알아서 등록해주지만, Karpenter가 띄우는 셀프 관리 EC2는 그렇지 않습니다 — `type = "EC2_LINUX"` Access Entry를 직접 만들어야 합니다. `modules/compute/karpenter/main.tf`에 `aws_eks_access_entry.karpenter_node` 리소스로 추가.

**⑥ Karpenter 컨트롤러가 launch template을 만들다 `ec2:CreateTags` UnauthorizedOperation**

Karpenter 공식 최소 IAM 정책은 "이미 `karpenter.sh/nodepool` 태그가 붙은 리소스"에 대한 `CreateTags`(`AllowScopedInstanceManagement`)와, "지금 막 생성되는 리소스"에 대한 `CreateTags`(`AllowScopedResourceCreationTagging`, `ec2:CreateAction` 조건으로 스코프)를 **별도 statement**로 나눠서 요구하는데, 후자가 빠져 있었습니다. launch template을 만들면서 동시에 태그를 붙이려는 요청은 "아직 그 태그가 없는" 리소스에 대한 요청이라 전자로는 커버가 안 됩니다(닭-달걀 문제). `modules/compute/karpenter/main.tf`에 `AllowScopedResourceCreationTagging` statement를 추가.

**⑦ Karpenter 노드에서 앱이 DB/Redis에 연결 못 함 (Hibernate `Unable to determine Dialect`, connection timeout)**

`modules/base/vpc`가 만드는 `app_security_group_id`(EKS 노드/Pod 공용 SG — Aurora/RDS Proxy/Valkey/EC2 PostgreSQL이 전부 "이 SG에서 오는 트래픽만 허용"하는 기준)를, 정작 노드에 아무도 안 붙이고 있었습니다. `eks_cluster`의 시스템 노드그룹도, `karpenter`의 EC2NodeClass도 EKS 클러스터 기본 SG(`cluster_security_group_id`)만 썼습니다 — 노드↔control plane 통신은 되지만 데이터 계층 접근은 전부 막힘. `karpenter` 모듈의 `securityGroupSelectorTerms`에 `app_security_group_id`를 추가로 붙이도록 고쳤습니다(`node_security_group_id`, `app_security_group_id` 둘 다 attach — selectorTerms는 나열하면 매칭되는 SG가 전부 붙는 OR 매칭).

**이미 떠 있던 노드에는 소급 적용 안 됩니다** — 이 변경을 반영한 뒤엔 `kubectl get nodeclaims`로 기존 노드를 확인하고 `kubectl delete nodeclaim {name}`으로 지워서 새 스펙으로 재생성시켜야 합니다. (당시엔 시스템 노드그룹은 이 SG가 없어도 CoreDNS/Karpenter 컨트롤러만 도니 괜찮다고 판단했는데, 이 판단이 아래 ⑬의 오배치 문제로 이어졌습니다.)

**⑧ `ExternalName` Service에 IP를 넣으면 DNS가 `NXDOMAIN`**

`k8s/base/04-db.yaml`의 `db-primary-service`/`db-reader-service`는 `type: ExternalName`인데, 이 타입은 **DNS 호스트네임만 허용**합니다(내부적으로 CNAME 레코드를 만드는 것과 같음) — IP 주소를 넣으면 생성은 되지만 CoreDNS가 못 풀어서 `UnknownHostException`/`NXDOMAIN`이 납니다. dev는 Aurora 대신 EC2 PostgreSQL을 쓰는데, `AURORA_ENDPOINT`/`AURORA_READER_ENDPOINT` GitHub Variable에 그 EC2의 **프라이빗 IP**가 그대로 들어가 있었던 게 원인이었습니다. EC2의 **프라이빗 DNS 이름**(`ip-10-13-10-42.ap-northeast-2.compute.internal` 형식 — VPC의 `enableDnsHostnames=true` 필요, 이미 켜져 있음)으로 바꿔서 해결. **EC2 IP를 이런 곳에 쓸 일이 있으면 반드시 프라이빗 DNS 이름으로 변환해서 쓸 것.** prod는 실제 Aurora 클러스터 엔드포인트(원래부터 DNS 이름 형식)를 쓰므로 이 문제와 무관.

**⑨ `SQS_INGEST_QUEUE_URL`이 통째로 배선 누락 (Spring 순환 참조 에러)**

`ai_pipeline` 모듈이 `purchase_channel_url`(SQS 큐 URL) output은 만들면서 `ingest_channel_url`은 안 만들고 있었습니다(ARN만 있었음) — SSM 파라미터도, `sync-github-config.sh`의 등록 대상도, `main-cd.yml`의 env/VARS도 전부 이 값이 빠져 있었습니다. `k8s/catalog`, `k8s/ai`의 ConfigMap이 `${SQS_INGEST_QUEUE_URL}`을 참조하는데 치환이 안 돼 리터럴 문자열이 그대로 들어갔고, Spring이 이걸 자기 자신을 가리키는 플레이스홀더로 오인해 `Circular placeholder reference`로 기동 실패했습니다. `ai_pipeline` 모듈에 `ingest_channel_url` output 추가, SSM 파라미터·`sync-github-config.sh`·`main-cd.yml`에 배선 추가.

**⑩ `-target`으로 일부만 apply하면 경고 없이 리소스가 통째로 빠질 수 있음 — 배포 실패 시 진단 순서**

⑤⑥⑦⑨는 전부 최초 apply 때는 안 드러나다가, `-target`으로 좁혀서 재시도하거나 여러 번 부분 apply를 반복하는 과정에서 하나씩 나타났습니다. `terraform apply -target=...`은 그 리소스가 **명시적으로 의존하는** 것만 같이 적용하고, 같은 모듈 안에 있어도 의존 관계가 없는 리소스(IAM 정책, Access Entry 등)는 조용히 건너뜁니다 — "Applied changes may be incomplete" 경고가 뜨긴 하지만 정확히 뭐가 빠졌는지는 알려주지 않습니다. **전체 `plan`/`apply`를 반드시 끝까지 실행해서 이 경고가 더 이상 안 뜨는 상태로 만들 것.**

또한 `main-cd.yml`의 `Rollback on failure` 스텝은 `Wait for rollout` 타임아웃(=실패로 간주) 시 자동으로 `kubectl rollout undo`를 실행해서 **더 예전(더 고장난) 이미지로 되돌립니다** — 새 이미지가 실제로 뭘 하다 죽었는지 확인하려면 롤백되기 전에(타임아웃 600초 이내) `kubectl logs --previous`로 봐야 하고, 이미 롤백됐다면 `kubectl set image deployment/{name} {container}={새 이미지}`로 직접 재배포해서 로그를 다시 확인하는 게 빠릅니다.

원인이 계층별로 겹쳐 있었다는 점도 참고할 것 — 하나 고치고 재배포해도 다음 계층의 문제(IAM → 네트워크 → DNS → 환경변수)가 순서대로 드러났고, 아래 2026-08-21 오후 사건에서 같은 패턴이 한 번 더 반복됩니다.

## 2026-08-21 (오후) — "1:1 채팅이 안 된다" 장애 대응

1:1 채팅 상담 기능이 안 된다는 리포트를 계기로 dev 클러스터를 점검하다가, 계층이 다른 배포 차단 버그가 순서대로 드러났습니다(위 ⑩과 같은 패턴). 여러 세션이 동시에 다른 계층을 나눠서 진행했습니다.

**⑪ (해결, PR #64) `CHAT_ALLOWED_ORIGINS`가 CI 배선에서 통째로 빠져 채팅 WebSocket이 전부 거절됨**

`k8s/ai/configmap.yaml`의 `CHAT_ALLOWED_ORIGINS: "${CHAT_ALLOWED_ORIGINS}"`는 `/ws/ai/chat` 핸드셰이크의 유일한 Origin 방어선(`WebSocketConfig.setAllowedOriginPatterns` — WS는 preflight가 없어 Ingress CORS가 안 먹힘)인데, `main-cd.yml`의 `ai` 배포 스텝(env 블록과 envsubst VARS 목록 둘 다)에 이 변수가 아예 없었습니다. `envsubst`는 VARS 목록에 없는 `${VAR}`는 손대지 않으므로, 배포된 ConfigMap에 리터럴 문자열이 그대로 들어갔고 — 실제 브라우저 Origin과 맞을 리 없어 핸드셰이크가 항상 403으로 거절됐습니다(dev 클러스터에 배포된 ConfigMap 값으로 직접 확인). `FRONTEND_ORIGIN`과 값이 같아야 하므로 새 GH Variable 없이 재사용하도록 배선.

**⑫ (해결) `AI_DB_NAME` GitHub Variable 미등록 + dev EC2 Postgres에 스키마가 하나도 없었음**

두 가지가 겹쳐서 `ai`/`member`/`order` 파드가 전부 DB 연결 단계에서 죽었습니다.

- `scripts/sync-github-config.sh`가 `AI_DB_NAME`을 "Terraform엔 DB 하나(bookdb)뿐이니 AI 전용 DB명이 따로 있으면 직접 등록하라"는 경고만 찍고 의도적으로 스킵했는데, 실제로 등록한 사람이 없었습니다. `main-cd.yml`의 `ai` 배포 스텝엔 `AI_VECTOR_BUCKET`/`EBOOK_S3_BUCKET`과 달리 이 값에 대한 필수값 가드(`exit 1`)가 없어 빈 값이어도 조용히 배포가 진행됐습니다. 결과: JDBC URL의 DB명이 빈 문자열이 되고, PostgreSQL은 dbname 미지정 시 접속 계정명으로 기본 처리하므로 `FATAL: database "bookadmin" does not exist`로 죽었습니다. `AI_DB_NAME=bookdb`로 등록해 해결 — `sync-github-config.sh`도 더 이상 스킵하지 않도록 고쳤습니다.
- `db/postgres/00-init.sql`(스키마 4개 + 서비스 계정 4개 + 권한) ~ `04-ai_db.sql`(테이블 DDL)이 저장소엔 있는데, **dev/prod 실인프라에 적용된 적이 한 번도 없었습니다.** `terraform/modules/dev_tools/ec2_postgres/main.tf`의 `user_data`는 "스키마 적용은 배포 파이프라인 몫"이라고 주석으로 떠넘겨 놨는데, 어떤 CI 워크플로에도 이 SQL을 실행하는 스텝이 없었습니다 — 로컬 docker-compose만 Postgres 공식 이미지의 `/docker-entrypoint-initdb.d/` 최초-기동 컨벤션으로 자동 실행되고 dev/prod는 해당 없음. dev EC2 Postgres에 SSM Session Manager로 접속해 `00-init.sql`부터 순서대로 수동 실행해서 해결(SQL 자체는 `IF NOT EXISTS` 가드가 있어 재실행 안전). **CI에 스키마 적용 스텝을 아예 추가할지, 계속 수동 런북으로 둘지는 아직 미결정.**

두 항목 해결 후 `catalog`/`member`/`order`는 전부 `1/1 Running`, 재시작 0회로 안정화된 것을 직접 확인했습니다.

**⑬ (해결, PR #62/#63/#65) 그 다음 계층 — 노드 스케줄링, Redisson TLS, IRSA**

DB/스키마가 뚫린 뒤 순서대로 드러난 문제 3건:

- **시스템 노드그룹 오배치** (PR #62): EKS 관리형 "system" 노드그룹(t3.medium, CoreDNS/Karpenter 컨트롤러용)에 taint가 없어서 `ai`/`member`/`order` 파드가 여기로도 스케줄링될 수 있었는데, 이 노드그룹엔 `app_security_group_id`가 안 붙어 있어(⑦의 수정이 이 노드그룹까진 커버 안 함) DB/Redis 연결이 막혔습니다. taint 추가 + 앱 워크로드에 Karpenter 노드용 toleration을 배선.
- **order-api Redisson이 TLS 없이 ElastiCache에 접속** (PR #63): Spring Data Redis(Lettuce, catalog/ai가 씀)는 `spring.data.redis.ssl.enabled`를 자동으로 따라가지만, 재고 차감 분산 락 전용인 Redisson(`RedissonConfig`, order 전용)은 별도 클라이언트라 이 값을 안 읽고 `"redis://"`(평문)로 하드코딩돼 있었습니다. Valkey가 `transit_encryption_enabled=true`(TLS 강제)라 평문 연결의 PING이 응답 없이 타임아웃되며 기동이 영원히 멎었습니다 — 기존 `ssl.enabled` 프로퍼티를 재사용해 `rediss://` 스킴을 선택하도록 수정. *(배포된 JAR을 직접 까서 구버전 클래스가 들어있는 걸 확인하는 방식으로 "이미 코드엔 있는데 왜 재현되지"를 검증했습니다 — 배포 이미지가 이 수정보다 오래된 커밋이었을 뿐이었습니다. 아래 진단 팁 참고.)*
- **ai-rag/ai-bot IRSA ServiceAccount 누락 + `AI_EPUB_BUCKET` 순환 참조 + member startupProbe 상한 부족** (PR #65): `ai_service_iam` 모듈이 IAM Role은 만들지만 그 Role을 참조하는 k8s `ServiceAccount`가 없어서 두 Deployment 모두 `default` SA로 뜨고, AWS SDK 자격증명 체인이 통째로 비어 `SdkClientException`으로 기동 즉시 죽었습니다 — `k8s/ai/serviceaccount.yaml` 신규 추가 + Role ARN을 SSM→GH Variable(`AI_SERVICE_IRSA_ARN`)→envsubst로 배선. 같은 PR에서 `AI_EPUB_BUCKET`의 ⑨와 동일한 패턴(CI에 없는 변수 참조로 리터럴 박힘, `EBOOK_S3_BUCKET` 재사용으로 수정)과, `member`만 `startupProbe.failureThreshold`가 60초로 남아있던 것(다른 서비스와 같은 180초로 통일)도 같이 고쳤습니다. prod의 `02-runtime`도 코드는 동일하게 고쳐뒀지만 **prod는 아직 미배포 — 처음 띄울 때 이 PR이 이미 반영된 상태여야 같은 문제를 안 겪습니다.**

**⑭ (미해결) Karpenter/시스템 노드 Role에 CloudWatch Logs·X-Ray 쓰기 권한 없음**

`lion-team3-dev-karpenter-node`/`lion-team3-dev-eks-node` Role 둘 다 Application Signals 로그 그룹/X-Ray 쓰기 권한이 없어서, OTel 사이드카가 파드 로그·트레이스를 CloudWatch로 못 보냅니다. 앱 자체의 기동/요청 처리는 안 막히지만(에러는 파드 로그엔 남음), CloudWatch 대시보드·X-Ray는 비어 보이니 "관측성 데이터가 왜 없지"로 헷갈리기 쉽습니다. IAM 정책에 `logs:PutLogEvents`/`xray:PutTraceSegments` 추가 필요.

**⑮ (진행 중, PR #67 draft) GitHub Actions Variables/Secrets가 레포 레벨 하나뿐 — dev/prod 전환마다 값이 서로 덮어씀**

`main-cd.yml`은 GitHub Environments를 안 쓰고 레포 레벨 Variables/Secrets 하나만 참조했습니다(`scripts/sync-github-config.sh` 자체 주석에 명시). `./scripts/sync-github-config.sh dev`로 dev 값을 채운 뒤 나중에 `prod`로 다시 돌리면 `EKS_CLUSTER`/`AURORA_ENDPOINT`/`AWS_COGNITO_USER_POOL_ID`/`REDIS_HOST`처럼 두 환경이 다른 값을 쓰는 항목이 전부 prod 값으로 덮어써지고, dev를 다시 배포하려면 스크립트를 dev로 재실행해야 하는 구조였습니다. dev/prod를 나란히 놓고 비교 테스트(예: RDS Proxy 유무 비교)할 계획이라 우선순위를 올림.

**PR #67**로 GitHub Environments(`dev`/`prod`) 도입 작업 중 — `workflow_dispatch`에 `environment` 입력 추가, `base`/`deploy`/`deploy-frontend` job에 `environment:` 지정, `concurrency` group도 환경별로 분리(prod 배포가 dev 배포를 취소 안 시키게), `sync-github-config.sh`가 `--env`로 등록하도록 수정. **머지 전 repo admin 권한으로 두 Environment를 만들고 값을 채워야 함** — Environment 생성은 admin 권한이 필요해서(`HTTP 403`으로 확인) 일반 write 권한 계정으론 못 함, draft 상태 유지 중.

**⑯ (해결, PR #68) ai-service IAM에 `s3vectors:GetIndex` 권한 누락**

⑬의 IRSA 수정으로 자격증명 교환까지는 성공했는데, 그 다음 단계에서 `AccessDeniedException: ...assumed-role/lion-team3-dev-ai-service/... is not authorized to perform: s3vectors:GetIndex`로 또 죽었습니다. 앱이 기동 시점에 인덱스 검증(차원·거리척도 확인, `k8s/ai/configmap.yaml`의 `AI_VECTOR_INDEX` 주석 참고)으로 `GetIndex`를 호출하는데, `ai_service_iam` 모듈의 `S3VectorsReadWrite` statement엔 `GetVectors`/`PutVectors`/`QueryVectors`만 있고 `GetIndex`가 없었습니다(§7.5 가이드 작성 시점엔 "실제 액션명은 나중에 AWS 문서로 확정"이라고 남겨뒀던 부분 — 확정이 안 된 채 방치됨). `GetIndex` 추가, dev apply 완료.

**⑰ (해결, PR #68) 벡터 인덱스 이름 불일치 — 앱이 부르는 이름과 실제로 만들어진 인덱스 이름이 다름**

⑯을 고쳐도 여전히 못 떴습니다. `aws s3vectors list-indexes`로 dev 버킷(`lion-team3-dev-vectors`)을 확인한 결과, 실제 인덱스 이름은 `recommendation`/`purchased-book-rag`(§7.5 가이드, terraform.tfvars와 일치)였는데, 앱이 실제로 부르는 인덱스 이름(`application.yml` 기본값, `k8s/ai/configmap.yaml`)은 `recommendation-books-v1`/`wiki-v1`으로 서로 달랐습니다. `purchased-book-rag`/`purchased_book_rag`는 terraform 쪽에만 있고 Java 코드/리소스 어디에도 참조가 없어 죽은 이름이었습니다.

dev의 두 인덱스는 벡터 0개(완전히 빈 상태)였어서 재인제스트 걱정 없이 앱이 부르는 이름(`wiki-v1`, `recommendation-books-v1`)으로 새로 만들어 해결(같은 dimension=1024/float32/cosine). terraform.tfvars의 ARN도 갱신, §7.5 가이드도 올바른 이름으로 수정.

**⑱ (해결) 새로 만든 `wiki-v1` 인덱스에 `non-filterable-metadata-keys` 설정 누락**

⑰을 고쳐 인덱스를 재생성한 뒤에도 `wiki-v1`이 `VectorIndexVerifier`에서 또 크래시했습니다. 앱은 `application.yml`(`non-filterable-metadata-keys: [text]`)을 기대하는데, `aws s3vectors create-index` 명령에 이 옵션을 안 넣고 만들어서 새 인덱스엔 그 설정이 빠져 있었습니다. 벡터 0개 재확인 후 삭제 → `--metadata-configuration nonFilterableMetadataKeys=text`로 재생성해 해결. **§7.5 가이드의 `create-index` 예시 명령어에 `--metadata-configuration` 옵션이 빠져 있었던 게 근본 원인이라 가이드도 갱신 필요** — 이걸 반영하고서야 ai-rag/ai-bot 최종 `1/1 Ready` 확인.

**⑲ (미해결) KakaoPay 결제 콜백 URL이 프로덕션 배선에서 전부 빠짐 — `localhost:5173`으로 리다이렉트됨**

`backend/apps/order-api/.../application.yml`의 `kakaopay.frontend-callback-url: ${KAKAOPAY_FRONTEND_CALLBACK_URL:http://localhost:5173/payments/kakao/callback}`을 `k8s/order/configmap.yaml`, `main-cd.yml`, `sync-github-config.sh` 어디에도 배선한 적이 없습니다(`docker-compose.yml`에만 있음 — 로컬 전용). `RealKakaoPayClient.java`가 이 값으로 결제 승인/취소/실패 후 `approval_url`/`cancel_url`/`fail_url`을 만드므로, 실제 결제가 성공해도 카카오가 사용자를 `localhost:5173`으로 돌려보냅니다 — 결제 자체는 되지만 완료 화면을 못 보는 사용자 체감 장애. `FRONTEND_ORIGIN`(이미 배선됨, `https://dev.ajttk.com`)에 경로만 붙여 `${FRONTEND_ORIGIN}/payments/kakao/callback`으로 재사용해 해결(PR #72).

**⑳ (해결, PR #72) catalog가 `SERVICES_MEMBER_URL` 없이 떠서 member-service 호출 실패**

catalog-api의 `MemberNotificationClient`(`@FeignClient(url = "${services.member.url}")`)가 `SERVICES_MEMBER_URL`을 쓰는데, `k8s/catalog/configmap.yaml`엔 `SERVICES_ORDER_URL`/`SERVICES_AI_URL`만 있고 이 값이 빠져 있었습니다(order의 configmap엔 `SERVICES_CATALOG_URL`/`SERVICES_MEMBER_URL` 둘 다 있어서 대조적). 기본값(`http://localhost:8083`)으로 떨어져 파드 자기 자신을 호출 시도 — order 쪽 주석("기본값이 자기 자신을 가리켜 조용히 degrade된다")과 같은 패턴. `k8s/catalog/configmap.yaml`에 `SERVICES_MEMBER_URL: "http://member-service.lion-app.svc.cluster.local:8080"` 추가해 해결.

**㉑ (해결) `amazon-cloudwatch-observability` addon이 시스템 노드그룹 taint 때문에 새 클러스터에서 절대 못 뜸**

`02-runtime`을 destroy 후 처음부터 다시 만들어도 잘 배포되는지 검증하려고, dev의 VPC/DB/Redis(`00-base`/`01-data`)는 그대로 재사용하고 `02-runtime`(EKS/Karpenter/ALB/AI IRSA)만 별도로 떼어낸 `terraform/environments/sandbox`를 만들어 실제로 처음부터 apply해봤습니다(2026-08-22). `module.eks_cluster` 단계에서 `amazon-cloudwatch-observability` addon이 `DEGRADED` 상태로 20분 타임아웃 후 apply 자체가 실패했습니다:

```
InsufficientNumberOfReplicas: all deployments have all pods unscheduled
0/2 nodes are available: 2 node(s) had untolerated taint(s)
```

원인: 시스템 노드그룹의 `CriticalAddonsOnly` taint(PR #62)를 이 addon의 파드가 못 견딥니다. `coredns` addon엔 이미 정확히 같은 이유로 `configuration_values`에 toleration이 들어가 있었는데(taint 도입 당시 같이 고쳤음), `cloudwatch_observability` addon은 그때 빠뜨렸습니다. **dev에서 안 드러난 이유**: dev의 이 addon은 taint가 생기기 전에 이미 파드가 떠서 돌고 있었고, 이미 스케줄된 파드는 나중에 taint가 추가돼도 쫓겨나지 않습니다 — 클러스터를 **처음부터** 새로 만들 때만(정확히 이번 sandbox 드릴 같은 경우) 재현됩니다. `coredns`와 동일한 `configuration_values`(taint에 대한 toleration)를 추가해 해결 — `terraform/modules/compute/eks_cluster/main.tf`.

이 발견 자체가 이 sandbox 드릴의 존재 이유였습니다 — dev를 아무리 들여다봐도 안 보이고, 실제로 처음부터 만들어봐야만 드러나는 종류의 버그였습니다.

## 진단 팁 — 배포된 이미지가 최신 코드를 안 반영한 것 같을 때

오늘 여러 건이 "코드는 이미 고쳐져 있는데 왜 재현되지"로 헷갈렸습니다. `main-cd.yml`의 `Rollback on failure`(⑩ 참고)가 반복되면 여러 리비전의 이미지가 뒤섞여 떠 있을 수 있습니다. 의심되면:

```bash
# 1. 크래시 중인 파드가 실제로 어느 이미지(커밋 SHA 태그)를 쓰는지 확인
kubectl get pod -n lion-app {pod} -o jsonpath='{.spec.containers[0].image}'

# 2. 그 커밋이 의심되는 fix 커밋의 조상인지 확인
git merge-base --is-ancestor {fix-commit-sha} {image-tag-sha} && echo "포함됨" || echo "미포함(그 전 이미지)"

# 3. 필요하면 이미지 JAR을 직접 까서 실제 들어간 클래스/리소스 확인
kubectl run debug -n lion-app --image={같은 이미지} --restart=Never --command -- sleep 3600
kubectl exec -n lion-app debug -- sh -c 'unzip -l /app/app.jar | grep {클래스명}'
# 확인 끝나면: kubectl delete pod debug -n lion-app
```

"미포함"이면 그냥 재배포를 기다리면 되는 문제고, "포함"인데도 재현되면 진짜 새 버그입니다 — 둘을 구분하는 게 삽질을 줄이는 첫 단계입니다.
