# 프로젝트 기획서 v6

## 1. 프로젝트 개요

**프로젝트명**: 책 먹는 사자

**추진 배경**

* **동기**: 좋아하는 작가의 신간 한정판 이벤트를 기다리다, [구매하기] 버튼을 누르는 순간 서버 오류로 사이트가 튕겨 결국 구매에 실패한 경험이 있었습니다.
* **추진 목표**: 순간 트래픽 폭주 상황에서도 결제 라인이 튕기지 않고(고가용성), 단 1개의 재고 오류도 발생하지 않는(정합성) 클라우드 네이티브 아키텍처를 구축하고, 이를 k6 부하 테스트로 정량 검증하고자 본 프로젝트를 추진하였습니다.

**기술적 이점**

* 도메인 특성 다변화를 통한 'MSA 아키텍처' 최적의 실증 환경:
  * **기능별 도메인 격리**: 도서 쇼핑몰은 [도서탐색·추천, 주문·결제, 마이페이지·RAG, 리뷰, 문의채팅]처럼 각 기능별 도메인 특성과 데이터 흐름이 명확히 분리되는 서비스입니다.
  * **MSA 구조 검증**: 이종 워크로드를 독립된 마이크로서비스로 분리함으로써, [특정 도메인의 장애가 결제 시스템으로 전이되지 않는 장애 격리(Fault Isolation)]와 [주문/결제 서비스만 핀포인트로 확장하는 EKS HPA 오토스케일링]을 완벽히 실증할 수 있습니다.
* 고동시성(High Concurrency) 환경에서의 '데이터 정합성' 검증:
  * **극단적 경합 시나리오**: 한정판 도서 타임세일 시 단 1초 만에 수천 건의 동시 결제/재고 차감 요청이 DB로 쏟아지는 고동시성 트랜잭션 경합 환경이 성립합니다.
  * **기술적 정합성 검증**: DB 커넥션 고갈 및 락 병목을 방지하기 위한 Redisson 분산 락의 동작 유무 검증. 초당 수천 건의 쓰기 트래픽 속에서도 Amazon Aurora RDS의 Multi-AZ ACID 트랜잭션을 통해 재고 오버셀링(Overselling) 없이 100% 데이터 정합성을 유지하는지 한계점 측정.

**최종 목표**

1. **트래픽 급증 대응 (Traffic Spike Resiliency)**
   * 목표: 신간 오픈·할인 이벤트·작가 사인회처럼 평소엔 조용하다가 특정 시점에 트래픽이 폭증하는 서점 특성상, 자동으로 확장되는 인프라가 필요합니다. (EKS HPA + Aurora Multi-AZ 채택)
   * 검증 방법: k6 부하 테스트 도구를 활용해 홈/도서목록 API에 단계적 부하를 인가하고, HPA가 백엔드 Pod를 자동으로 증설하여 응답 시간(P95 Latency)을 안정적으로 유지하는지 확인합니다.
2. **DB 부하 분산 (Database Offloading)**
   * 목표: 베스트셀러·신간처럼 반복 조회되는 데이터까지 매번 DB가 처리하면 이벤트 트래픽에 버틸 수 없습니다. (ElastiCache for Redis를 통한 Caching 도입)
   * 검증 방법: 캐시 미적용 상태와 적용 상태로 도서 목록 API를 반복 호출하고, Aurora RDS의 CPU 사용률과 API 응답 시간의 격차를 비교 검증합니다.
3. **장애 복구 (Self-Healing & Fault Isolation)**
   * 목표: 트래픽이 몰릴 때 특정 Pod 하나가 다운되거나 장애가 발생해도 서비스 전체가 멈추면 안 됩니다. (EKS Self-Healing 및 MSA 장애 격리 활용)
   * 검증 방법: 고부하 유입 중 특정 마이크로서비스(예: AI/RAG Pod)를 강제 종료(kubectl delete pod)하고, 시스템 복구 소요 시간과 클라이언트 측 에러율(5xx)을 측정합니다.
4. **무중단 배포 (Zero-Downtime Deployment)**
   * 목표: 대규모 이벤트 기간 중에도 긴급 버그 패치나 기능 배포가 필요할 수 있습니다. (K8s Rolling Update를 통한 무중단 반영)
   * 검증 방법: 부하가 지속해서 유입되는 상황에서 신규 버전 배포를 실행하고, 서비스 다운타임이 0초인지 및 요청 성공률 100%를 유지하는지 확인합니다.
5. **결제 안정성 (Payment Reliability & ACID Integrity)**
   * 목표: 이벤트 시 결제가 몰리는 순간이 매출과 직결됩니다. (Multi-AZ 6중 자동 복제 및 빠른 Failover로 가용성을 확보하는 Aurora RDS와 L7 기반 트래픽 분산을 지원하는 ALB로 결제 구간 보호)
   * 검증 방법: 결제 API에 대규모 동시 요청을 인가하고, 재고 오버셀링 없이 응답 시간 준수 여부 및 결제 성공률(99.9% 이상)을 측정합니다.

## 2. 시나리오

### **사용자(Customer)**

1. **도서 탐색 및 취향 추천:**

* 비회원 상태로 홈 화면에서 베스트셀러, 신간, 분야별 도서를 탐색합니다.
* AI 맞춤 추천 스와이프 카드(좋아요/스킵)를 통해 개인 취향 도서를 추천받습니다.

2. **장바구니 및 계정 통합:**

* 비회원 상태에서 마음에 드는 도서를 장바구니에 담은 후 결제를 위해 로그인을 진행합니다.
* AWS Cognito 인증 성공 시 로컬 장바구니 데이터가 서버 장바구니로 안전하게 자동 병합(Merge)됩니다.

3. **주문 및 결제:**

* 보유한 쿠폰을 적용하여 할인을 받고, 배송지 입력 및 결제 수단(**자체 가상카드** 또는 **카카오페이 모바일 간편결제**)을 선택하여 결제를 완료합니다. *(※ 포인트 시스템은 쿠폰 단일 할인 체계로 통합)*

4. **마이페이지 & 게이밍 & RAG 질의:**

* 주문/배송 현황을 실시간 조회하고, 구매 확정된 도서에 대해 평점 및 리뷰를 작성합니다.
* 완독한 도서를 캐릭터(사자)에게 먹여 경험치를 획득하고 레벨을 올립니다.
* 독서 중 남긴 메모를 기반으로 RAG 질의(예: *"내가 메모한 내용 중 분산 트랜잭션 관련 핵심 내용 요약해줘"*)를 수행하여 AI 답변을 얻습니다.

5. **고객 지원:**

* 도서별 상품 Q&A 게시판 및 1:1 실시간 상담 문의(WebSocket + Redis Pub/Sub)를 통해 운영자와 소통합니다.

### **운영자(Admin)**

* **신간 등록 및 벡터 자동 파이프라인:** 관리자 콘솔에서 신간 및 줄거리/목차를 업로드하면, S3 이벤트가 AWS SQS로 전달되어 **AI 벡터 임베딩이 S3 Vectors에 자동 색인**됩니다.
* **프로모션 및 운영 관리:** 정기구독 이벤트 배너 관리, 쿠폰 정책(발급/할인율) 설정, 전체 주문/배송 상태 변경을 수행합니다.
* **어뷰징 방지 및 상담원 수행:** 구매 확정 사용자만 리뷰를 작성할 수 있도록 백엔드 검증을 관리하며, Cognito 관리자 권한(`ADMIN` 그룹)으로 1:1 실시간 문의 채널에 접속하여 고객 상담을 진행합니다. *(※ 미구현/보류 — 사용자 쪽 채팅 인프라는 구현돼 있으나, 관리자가 답하는 화면·저장소가 아직 없어 현재는 동작하지 않습니다. 상세는 `db-erd-v2.md`의 ai_db 섹션 참고)*

## 3. 도메인

## 마이크로서비스(MSA) 도메인 설계

```
                                    ┌─── Catalog DB (Schema)
   [ Client ] ──► [ ALB / WAF ]  ───┼─── Order DB   (Schema) ──► Aurora PostgreSQL (Multi-AZ)
                                    ├─── Member DB  (Schema)
                                    └─── AI DB      (Schema)
```

| **마이크로서비스** | **포함 세부 기능 (Sub-Domains)** | **주요 저장소 및 기술 스택** | **도메인 분리 및 설계 이유** |
| -- | -- | -- | -- |
| 1. 상품 도메인(Catalog Service) | • 도서 탐색/상세 (Book)• 구매인증 리뷰 (Review)&#10;• 위시리스트 (Wishlist)• 상품 문의 & FAQ API | • Aurora PostgreSQL (`catalog` 스키마)• ElastiCache for Redis (베스트셀러 캐싱)• Redis Streams (구매 이벤트 수신) | **Read-Heavy(전체 트래픽의 ~95%) 영역.**Redis 캐싱으로 DB I/O를 최소화하고, 주문 서비스와의 결합도를 낮추기 위해 Redis Streams 비동기 이벤트로 구매 확정 리뷰 권한을 검증함. |
| 2. 결제 도메인(Order & Payment) | • 장바구니 (Cart, 비회원 병합)• 쿠폰 할인 (Coupon)• 주문 트랜잭션 (Order)• 결제 처리 (Payment, 가상카드/카카오페이)• 배송 상태 관리 (Delivery) | • Aurora PostgreSQL (`order` 스키마)• ElastiCache for Redis (Redisson 분산 락)• Redis Streams (주문 완료 이벤트 발행) | **Write-Heavy 및 고동시성 트랜잭션 경합 영역.**재고 차감 시 Redisson 분산 락으로 오버셀링을 차단하고, 타 도메인 장애 시에도 결제 가용성을 100% 보호함. 포인트는 쿠폰으로 단일화. |
| 3. 사용자 도메인(Member Service) | • 회원 식별 (`cognito_sub` 기반)• 권한 인가 (`cognito:groups`)• 사자 캐릭터 레벨/경험치 (Lion) | • Aurora PostgreSQL (`member` 스키마)• AWS Cognito (User Pool / Token 검증) | **중앙화 인증 및 사용자 게이밍 영역.**Cognito의 `sub`(UUID)을 PK로 직접 매핑하여 DB 추가 조회를 최소화하고, JWT 토큰 클레임 기반의 무상태(Stateless) 인가를 수행함. |
| 4. AI 도메인(AI Service) | • 독서 메모 RAG 질의응답• AI 1차 상담 챗봇 (FAQ 기반)• AI 도서 취향 스와이프 추천• 1:1 실시간 상담 채팅 (Inquiry)• 도서 벡터 자동 색인 파이프라인 | • Aurora PostgreSQL (`ai` 스키마)• AWS S3 Vectors (벡터 저장소)• AWS SQS (벡터 인덱싱 이벤트)• AWS Bedrock (Embedding / LLM)• ElastiCache (Chat Redis Pub/Sub) | **Heavy CPU 연산 및 실시간 통신 격리 영역.**외부 LLM 호출 지연이 결제 시스템에 전이되지 않도록 Resilience4j Bulkhead로 차단. 분산 Pod 환경의 1:1 채팅 브로드캐스팅을 위해 Redis Pub/Sub 채택. |

### 3) 데이터베이스 및 인메모리 캐시 (Database & Cache)

| 기술 | 장점 | 단점 | 본 프로젝트 사용 이유 |

### 5) 왜 Docker/VM 단독이 아닌 EKS(Kubernetes)인가?

**기술별 성능 및 운영 비교표**

| 비교 항목 | VM(EC2 단독) | Docker(Single Node) | Amazon EKS(Kubernetes) |
| -- | -- | -- | -- |
| 자가 치유(Self-Healing) | X(서버 다운 시 직접 SSH 접속 후 재부팅) | △(restart: always로 프로세스만 재시작) | O(노드/Pod 장애 시 3초 내 다른 노드에 자동 재배치) |
| 오토스케일링 | △(EC2 단위 확장, 분 단위로 느림) | X(수동 컨테이너 추가 필요) | O(초 단위 자동 확장: HPA, Karpenter) |
| 무중단 배포 | X(직접 스크립트 작성, 다운타임 발생) | △(배포 순간 1~2초 서비스 끊김 발생) | O(Rolling Update를 통한 다운타임 0초 완전 구현) |
| 운영 난이도·비용 | O(쉬움/저렴) | O(쉬움/저렴) | X(어려움/컨트롤 플레인 비용 발생) |

**Docker/VM 단독 운영 시 한정판 타임세일에서 겪게 되는 3대 장애 시나리오**

1. **타임세일 순간 서버 다운 발생 시(자가 치유 부재)**
   * Docker만 사용할 때: 자정 00시 00초에 접속자가 몰려 메모리 고갈로 서버가 다운되면, 개발자가 깨어나 SSH 접속 후 docker-compose up을 실행할 때까지 모든 고객의 결제가 실패하고 접속이 차단됩니다.
   * EKS를 사용할 때: 특정 Pod나 노드가 다운되는 즉시 EKS가 이를 감지하여, 정상 작동 중인 다른 노드에 동일한 Pod를 3초 만에 자동 재생성하여 서비스를 유지합니다(Self-Healing).
2. **이벤트 기간 버그 패치 및 RAG 프롬프트 배포 시(무중단 배포 부재)**
   * Docker만 사용할 때: 배포를 위해 기존 컨테이너를 종료(stop)하고 새 컨테이너를 실행(start)하는 수 초 동안 [구매하기] 버튼을 누른 고객들에게 500 에러 화면이 노출됩니다.
   * EKS를 사용할 때: 10개의 Pod 중 2개씩 순차적으로 교체하는 Rolling Update를 수행하여 고객이 배포 여부를 인지하지 못한 채 정상 결제를 완료하도록 지원합니다.
3. **1초 만에 트래픽이 100배 몰릴 때(오토스케일링 부재)**
   * Docker만 사용할 때: 작업자가 직접 AWS 콘솔에 접속해 EC2 인스턴스를 추가 프로비저닝하고 로드밸런서에 수동 연동해야 하므로 대응 지연이 발생합니다.
   * EKS를 사용할 때: HPA가 RPS/CPU 증가를 감지하여 Order Pod만 즉시 2개에서 50개로 핀포인트 수평 확장을 진행합니다.

**Kubernetes(EKS) 도입의 4대 핵심 명분(MSA 연계)**

* **MSA 도메인 오케스트레이션 및 장애 격리(Fault Isolation)**: 도서탐색·추천, 주문·결제, 마이페이지·RAG, 리뷰, 문의채팅 도메인을 물리적으로 분리 배포합니다. RAG 질의응답이나 AI 추천 로직에 부하가 몰려 CPU가 100%에 도달하더라도, 독립된 Order/Payment Pod는 영향을 받지 않고 결제 트랜잭션을 완수합니다.
* **도메인별 핀포인트 오토스케일링(Pinpoint Auto-Scaling)**: 거대 단일(Monolith) 서버 전체를 확장할 필요 없이, 타임세일 시 트래픽이 몰리는 Order/Payment Pod만 핀포인트로 확장하여 인프라 비용을 대폭 절감합니다.
* **24시간 무중단 서비스 및 신속한 튜닝 반영(Zero-Downtime Patch)**: AI RAG 프롬프트나 추천 알고리즘 튜닝 시 결제 시스템에 영향을 주지 않고 Rolling Update로 무중단 즉시 반영합니다.
* **선언적 인프라 관리(GitOps 연동 확장성)**: Helm 및 ArgoCD와 연동하여 클러스터 상태를 코드(YAML)로 선언적 관리함으로써 배포 실수 및 운영 장애 위험을 차단합니다.

### 6) 왜 단일 배포(Monolithic Deployment)가 아닌 MSA(Microservices Architecture)인가?

**1. 기술별 성능 및 운영 비교표**

| 비교 항목 | 단일 배포(Monolithic Deployment) | MSA(Microservices Architecture) |
| -- | -- | -- |
| 배포 단위 | 전체 애플리케이션 단일 아티팩트(Single JAR/WAR) | 도메인별 독립 컨테이너 단위 |
| 장애 격리(Fault Isolation) | X(특정 도메인 장애 발생 시 전체 서비스 마비) | O(서비스 간 완벽 격리로 특정 파드 다운 시에도 타 서비스 정상 작동) |
| 오토스케일링 | △(애플리케이션 전체 자원 단위 확장으로 자원 낭비 발생) | O(트래픽 집중 도메인만 핀포인트 수평 확장: HPA) |
| 배포 위험도 | X(소규모 코드 수정 시에도 전체 서비스 재부팅 필요) | O(특정 마이크로서비스만 독립 무중단 배포: Rolling Update) |
| 자원 최적화 | X(모든 로직이 동일한 CPU/RAM 자원 사양 공유) | O(도메인 특성에 맞춘 파드 자원 및 Thread Pool 최적 할당) |

**2. 단일 배포 구조 운영 시 한정판 타임세일에서 겪게 되는 3대 장애 시나리오**

1. **RAG 질의응답 및 AI 추천 요청 폭주 시(장애 격리 부재)**
   * 단일 배포 적용 시: Heavy CPU 워크로드인 RAG 질의응답 트래픽이 폭주하여 서버 CPU가 100%에 도달할 경우, 동일한 애플리케이션 내에서 실행 중인 결제 및 주문 기능까지 쓰레드가 고갈되어 함께 마비됩니다.
   * MSA 적용 시: AI/RAG 서비스 파드가 고부하로 인해 지연되거나 다운되더라도, 물리적으로 분리된 결제/주문 파드(Order/Payment Pod)는 단 0.1%의 영향도 받지 않고 정상 작동하여 결제 가용성을 유지합니다.
2. **AI 프롬프트 및 추천 로직 패치 시(배포 위험도)**
   * 단일 배포 적용 시: AI 추천 알고리즘이나 프롬프트 문구 하나를 수정하더라도 결제 및 회원 시스템이 포함된 전체 애플리케이션을 재부팅해야 하므로, 배포 시 장애 위험도가 극도로 높아집니다.
   * MSA 적용 시: 결제 라인에 영향을 주지 않고 AI 추천 서비스 파드만 K8s Rolling Update를 통해 24시간 무중단으로 안전하게 독립 배포합니다.
3. **타임세일 순간 결제 트래픽 집중 시(스케일링 및 자원 비효율)**
   * 단일 배포 적용 시: 결제 트래픽만 증가하였음에도 무거운 전체 애플리케이션 인스턴스 단위를 통째로 늘려야 하므로, 서버 프로비저닝 속도가 느리고 컴퓨팅 자원이 크게 낭비됩니다.
   * MSA 적용 시: 트래픽이 집중되는 결제/주문 파드만 핀포인트로 2개에서 50개로 초단위 수평 확장(HPA)하여 인프라 비용을 극대화하여 절감합니다.

**3. MSA(Microservices Architecture) 도입의 4대 핵심 명분**

* **완벽한 장애 격리(Fault Isolation)**: 도서탐색·추천, 주문·결제, 마이페이지·RAG, 리뷰, 문의채팅 도메인을 물리적으로 분리 배포하여 특정 서비스의 장애가 결제 시스템으로 전이되는 것을 근본적으로 차단합니다.
* **도메인별 핀포인트 오토스케일링(Pinpoint Auto-Scaling)**: 거대 단일 서버 전체를 확장할 필요 없이, 타임세일 시 트래픽이 몰리는 주문/결제 파드만 핀포인트로 확장하여 자원 효율성을 극대화합니다.
* **독립적 무중단 배포(Independent Zero-Downtime Deployment)**: AI 프롬프트나 추천 로직 등 튜닝이 잦은 영역을 결제 시스템 영향 없이 Rolling Update로 무중단 즉시 반영합니다.
* **도메인 특성별 자원 최적화(Resource Optimization)**: In-Memory 중심의 Caching/채팅 서비스와 Heavy CPU 중심의 RAG 서비스에 각각 최적화된 파드 자원 사양(CPU/RAM)을 다르게 할당하여 효율적으로 운영합니다.
